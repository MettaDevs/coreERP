# PF-01: pembuatan tenant tanpa pemasangan ERP

PF-01 memisahkan penciptaan tenant kanonik dari registrasi ERP. Principal yang sudah ada dapat mempunyai tenant baru tanpa akun kedua. Tenant-only menyimpan client, tenant, membership, receipt dan audit, tanpa membuat role ERP, satuan, entitlement, environment atau instalasi module.

Status verifikasi akhir dan PR dicatat pada [TODO portal](TODO.md). Unit ini tidak memisahkan database fisik. Urutan sesudahnya mengikuti [HANDOFF CPDB](../control-plane-database/HANDOFF.md).

## Perbedaan operasi

| Operasi                    | Hasil                                                                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pembuatan tenant kanonik   | Metadata pusat dan satu membership untuk principal yang ditetapkan. Tidak memasang ERP.                                                                                   |
| Registrasi ERP             | Membuat akun password jika jalur tersebut memerlukannya, memakai pembuatan tenant yang sama, kemudian menjalankan bootstrap ERP.                                          |
| Bootstrap ERP              | Menyiapkan Owner ERP, duty/scope, satuan, entitlement dan environment yang dipilih. Pemasangan module tetap memeriksa environment serta module yang benar-benar tersedia. |
| Pembuatan fasilitas Faskes | Masih memakai resource UUID yang ada. Pemetaan resource tersebut ke tenant kanonik merupakan PF-02.                                                                       |

Membership aktif dan audit creator tidak menjadi permission pengelolaan tenant. Catalog/assignment pengelolaan, undangan, grant environment dan revoke tetap pekerjaan PF-04. Tidak ada `system_role` atau owner flag baru pada membership.

## Satu writer melalui kontrak tenant

Desain membandingkan writer terpisah dengan operasi tenant-only pada `RegisterBusiness` yang sama. Writer terpisah dipilih agar perubahan bootstrap ERP tidak menyusup ke pembuatan metadata. Keduanya mempertahankan satu writer dan caller ERP lama. Authorization sebelum replay serta fingerprint owner/payload diambil sebagai kontrak bersama. Perbandingan memakai dua kandidat dan judge dengan model yang sama.

`TenantRegistrar` pada `App\Platform\Tenant\Contracts` adalah batas yang dipakai domain registrasi. Pelaksananya, `App\Platform\ControlPlane\Tenants\CreateTenant`, memiliki penulisan client, tenant, membership awal dan receipt pusat.

Pemilik tersebut penting karena package ControlPlane tidak boleh diimpor langsung oleh fitur Platform lain. `RegisterBusiness` bergantung pada kontrak tenant, bukan model Client. Binding pelaksana dilakukan provider ControlPlane. Pengecualian lama `RegisterBusiness` ke Client dihapus dari penjaga arah dependency.

`TenantCreation` mengembalikan tenant, membership, principal dan flag replay secara eksplisit. Caller tidak mencari tenant melalui membership pertama atau yang paling baru. `BootstrapErpTenant` menerima hasil tersebut untuk operasi ERP. `RegisterBusiness` tetap merupakan registrasi ERP bagi caller lama dan bootstrap on-prem.

Event `TenantCreated` sekarang hanya menyatakan metadata tenant telah dibuat. Seed satuan mendengarkan `ErpTenantInitialized`, sehingga pembuatan tenant-only tidak memicu penulisan data bisnis. Payload event module dan versi `core.tenant.provisioned.v1` tetap mengikuti kontrak yang ada.

## Principal dan identity

`users.id` bigint tetap menjadi principal bersama. `product_customers.user_id` nullable menyimpan binding eksplisit dari UUID pendaftaran produk. Login biasa tidak membuat User. Binding dilakukan saat customer meminta tenant kanonik.

Resolver membaca pasangan `issuer + subject` aktif. Exact identity memakai User PERSON yang sama. Jika belum ada, email kontak yang telah diverifikasi dapat dipakai untuk membuat akun baru beserta external identity. Email tidak dipakai untuk menemukan atau mengambil alih akun lama.

Dua subject dengan email provider sama tidak digabung. Keduanya dapat memakai kontak terverifikasi berbeda sesuai constraint yang sudah ada. Jika email credential sudah dipakai User lain tanpa exact identity, creation ditolak dengan konflik linking. Tidak ada email fiktif atau pelonggaran unique email. Binding bertentangan atau identity yang diarsipkan juga ditolak.

## Endpoint dan actor

| Endpoint                                                   | Boundary                                                                                                                                                             |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/internal/v1/tenant-registrations`               | Token pusat admin, `requested_by` operator dan `owner_user_id` eksplisit. Core memeriksa provider access operator.                                                   |
| `POST /api/internal/v1/product-registration/organizations` | Gateway token dan session customer yang masih sah. Principal dan actor berasal dari session tersebut.                                                                |
| `POST /api/internal/v1/tenants`                            | Registrasi ERP lama. Konsol meneruskan operator dari session server melalui `requested_by`. Caller token-only lama dicatat sebagai system bila tidak menyebut actor. |

Request tenant-only memuat `name`, `slug` dan `idempotency_key`. Field tenant/client ID, owner/actor customer, role, status, entitlement dan pilihan environment dari browser ditolak. Response memuat `tenant_id`, `membership_id`, `principal_id` dan `replayed`, dengan status 201 untuk creation dan 200 untuk replay.

Operator dan owner merupakan principal yang berbeda bila operator membuat tenant bagi orang lain. Tidak ada fallback owner ke operator. Audit `tenant.created` mencatat actor, principal pemilik, membership dan receipt pada transaksi creation yang sama. Field actor pada konsol diambil dari user yang telah login, bukan dari form.

Kedua endpoint kanonik hanya membuat metadata. Keduanya tidak memanggil provisioner fasilitas atau mengubah enrollment dan tenant yang ditakedown.

## Retry, slug dan transaksi

`tenant_creation_requests` menyimpan scope actor, idempotency key, fingerprint request, actor/principal serta tenant/membership hasil. Unique scope dan key adalah identitas teknis replay yang tetap dipertahankan.

Authorization diperiksa sebelum hasil replay diberikan. Key dan payload sama mengembalikan ID yang sama. Key sama dengan owner atau payload berbeda ditolak. Slug eksplisit yang bertabrakan menghasilkan konflik; lock namespace dan unique index menjadi penjaga concurrency. Slug otomatis caller ERP lama tetap memakai allocator nama yang ada.

Replay tidak mengaktifkan tenant atau membership yang sudah ditutup. Creation principal, binding, canonical rows, receipt dan audit commit bersama pada koneksi pusat.

Registrasi ERP lama mempertahankan rollback seed bersama registrasi pada susunan satu database saat ini. Kode ini belum menjamin transaksi dua database, receipt adapter, atau recovery lintas database CPDB-03. On-prem tetap memakai authority lokal dan tenant ID tetap dari bootstrap yang tepercaya.

## Bukti verifikasi

Test behavior berada pada `apps/core/tests/Feature/Platform/Tenant/CanonicalTenantCreationTest.php`, beserta regresi operator, Foundation rollback, identity/SSO, Boundary, bootstrap on-prem dan suite konsol yang relevan.

`scripts/verify-tenant-creation.py` mengirim request HTTP nyata, lalu `scripts/tenant-creation-fixture.php` membaca row committed melalui koneksi PostgreSQL terpisah. Guard memeriksa environment, config dan database/schema aktual sebelum setup. Target URL juga harus cocok dengan port service Compose yang terpilih.

Pemeriksaan mencakup tenant kedua principal lama, binding principal baru, subject/email collision, tanpa efek ERP, actor terlarang, operator terpisah dari owner, replay dan race slug. Baseline ERP harus dipin ke revisi Git dan hash backend yang sesuai. Probe latency memeriksa principal terhadap fixture asal serta delta SQL, sehingga respons konsisten yang menunjuk pemilik salah tetap ditolak.

Database fixture terpisah dari database UI dan server. Source baseline serta source fitur dapat ditempatkan pada filesystem Linux Docker untuk menghindari biaya bind mount Windows saat pengukuran. Angka fixture tidak dianggap kapasitas production. Bukti `evidence/pf-01/http-acceptance.json` merekam 10 lane lulus dan 179 request HTTP. Probe 150 creation mengukur p95 509,470 ms, nol error, serta delta SQL 150 tenant dan membership tanpa User atau data ERP tambahan. Angka ini hanya latency absolut fixture pengembangan pada source backend `a4f331dd`; bukan kapasitas atau SLA production. Ringkasan command, source dan keterbatasan ada pada `evidence/pf-01/verification.json`.

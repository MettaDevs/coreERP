## Blocker

### [ ] `PLAT-01` — No workflow / approval engine anywhere — Procurement's primary documents cannot exist

**Jenis:** missing-core-capability · **Verifikasi:** CONFIRMED · **Memblokir:** procurement, management-aset, core-workflow, core-notification

- **Dynamics 365:** D365 F&O ships a platform Workflow module. Modules register workflow types (PurchReqReview, PurchaseOrder approval, VendInvoiceApproval); a tenant then designs a workflow version with approval steps, task steps, manual/conditional/parallel branches, automatic actions, escalation timers, time limits, delegation, ad-hoc insertion and recall. Approvers are resolved by participant provider, user hierarchy provider (managerial hierarchy from HcmWorker/position), organization hierarchy provider, or queue. Work items land in a single cross-module 'Work items assigned to me' inbox with Approve/Reject/Request change/Delegate, and every transition is written to workflow history. Purchase requisition, purchase order change management, and vendor invoice approval are unusable in F&O without it.
- **Keadaan sekarang:** Nothing. No workflow, workflow_version, workflow_instance, workflow_element, work_item, delegation, escalation or workflow_history table in any of the 24 migrations; no Workflow model among the 34 models in apps/control-plane/app/Models/; no work-item inbox in apps/control-plane/resources/js/pages/ or in the Web Shell; no work-item route in routes/web.php or routes/api.php. The word 'approval' appears in docs only, as an example of what a future feature would need (docs/dev/01-grand-design.md:100, docs/dev/05-customization-and-addons.md:10) or as a manual human sign-off gate (docs/dev/02-module-standard.md:136).
- **Bukti:** Searched apps/control-plane/database/migrations/** for workflow\|approval\|work_item\|delegation\|escalation: zero hits. apps/control-plane/app/Models/ (34 files, listed) has no workflow model. routes/web.php:1-172 and routes/api.php:1-11 expose no work-item or approval endpoint. Only doc mentions: docs/dev/01-grand-design.md:100, docs/dev/05-customization-and-addons.md:10, docs/dev/05-customization-and-addons.md:20, docs/dev/02-module-standard.md:136.
- **Kenapa penting:** Purchase requisition and purchase order are approval documents by definition; a procurement app whose requisition cannot be routed for approval has no product. Without a Core service, app 2 must build an approval engine, an approver resolver, a work-item inbox, delegation and escalation inside procurement_db — and then app 3 builds a second one, giving users two separate inboxes and the tenant two places to configure who may approve what. That is the single largest irreversible architecture mistake available to this project right now.
- **Perubahan yang diperlukan:** MUST be a Core service, and it can be one without violating the no-cross-database rule. Concrete design: (1) Core owns a new database-owned domain in the Control Plane — workflow_types (registered from app.yaml, validated in apps/control-plane/app/Http/Requests/Provider/AppCatalogRequest.php exactly like number_sequences.references at :38-43), workflow_configurations + workflow_configuration_versions (reuse the draft/published/effective-version pattern already proven by organization_hierarchy_versions and tenant_number_sequences), workflow_elements, workflow_instances, work_items, work_item_delegations, workflow_escalations, workflow_history. (2) Apps own the business document and a `workflow_state` column; Core never writes an app database and apps never read Core's workflow tables. (3) Submission protocol: app writes document + an outbox row in one app-database transaction (the identical rule already mandated for continuous number sequences at docs/dev/14-number-sequences.md:111), and a worker POSTs /internal/v1/workflow-instances through the existing AuthenticateAppService middleware with Idempotency-Key and a `decision_context` JSON payload. (4) THE key constraint that makes this work with no cross-database queries: conditional decisions, spending thresholds and branch conditions may evaluate ONLY over `decision_context` fields the app pushed at submission, whose JSON schema the app declares in app.yaml and Core validates. Core must never need to read the app's document to decide. Resubmission after 'request change' re-pushes the whole context. (5) Completion protocol: Core does not call back synchronously as the durable path — it emits core.workflow.instance-completed.v1 / rejected / recalled, the app's inbox consumer applies the transition idempotently, and the app's own state machine treats 'approved' as advisory until applied, so posting is never gated on an unverified callback. A registered sync callback URL in the manifest is allowed as a latency optimisation only. (6) Routing: role-based and organization-hierarchy-based routing can ship immediately because roles, role_assignment_org_scopes and organization_hierarchy_closures already live in Core. Managerial-hierarchy routing and budget/signing-limit routing are gated on workforce/position, which docs/dev/10-core-foundation-gates.md:12 already lists as absent — so signing limits (a Core-owned signing_limits table keyed by position/role + legal entity + currency + amount) must be sequenced after workforce, and Procurement's first release should use role + amount-threshold routing, not 'my manager'. (7) The work-item inbox is a Web Shell surface, not an app surface, because it is cross-app by nature (docs/dev/02-module-standard.md:117 already assigns the shared header to Web Shell). Reject the alternative of a packages/workflow library embedded per app: it forces hierarchy and signing-limit data to be replicated into every app database and gives each app its own inbox. Owner: Core (engine, registry, work items, inbox) + app (document state machine, decision_context, outbox, inbox consumer).

### [ ] `PLAT-02` — No document management, attachments, or document types — Asset cannot store photos/certificates, Procurement cannot store quotes/contracts

**Jenis:** missing-core-capability · **Verifikasi:** CONFIRMED · **Memblokir:** management-aset, procurement, core-document-management

- **Dynamics 365:** D365 F&O has DocuRef/DocuValue/DocuType: a document-handling framework where any record in any table can carry attachments; document types define whether the attachment is a file, note, URL or simple note, which storage location it uses (Azure Blob / SharePoint / database), whether it is restricted, and default file-type filters. Attachment visibility follows the record's own security, and the paper-clip control is a platform control available on every form.
- **Keadaan sekarang:** Nothing. No document, document_type, attachment, or file-reference table in any migration; no Storage:: call, no UploadedFile handling anywhere in apps/control-plane/app/. config/filesystems.php:16 is the untouched Laravel default (`local` disk, storage/app/private) with no tenant-scoped path convention and no S3 credentials wired. resources/js/components/ui/attachment.tsx exists but is an unused shadcn presentational component, not an attachment service. app-erp-management-aset has no upload UI (grep for upload\|attachment\|lampiran across D:/Kerja/app-erp-management-aset/ui/src returns nothing) and no attachment table in its 3 migrations.
- **Bukti:** apps/control-plane/config/filesystems.php:16,31-56 (stock defaults). grep -rn 'Storage::\|UploadedFile\|->file(' apps/control-plane/app/ → zero hits. apps/control-plane/database/migrations/** has no document/attachment table. D:/Kerja/app-erp-management-aset/database/migrations/ (3 files) has no attachment table. apps/control-plane/resources/js/components/ui/attachment.tsx is presentational only.
- **Kenapa penting:** An asset register without photos, purchase invoices, warranty certificates and calibration certificates is not an asset register — auditors ask for the certificate, not the row. A procurement app without vendor quotes and signed contracts attached to the RFQ/PO cannot support a tender process. If each app builds its own uploader, the tenant gets N storage configurations, N retention policies, N permission models, and on-prem customers get N places where files silently land on a container filesystem that is not in the backup set.
- **Perubahan yang diperlukan:** Core-owned metadata + shared storage contract, app-owned linkage. Core: document_types (per tenant: name, allowed MIME/extension list, max size, storage profile, restricted flag), storage_profiles (local path / S3-compatible bucket + credentials reference, distinct per deployment profile so on-prem uses a mounted volume), and a signed-URL issuing endpoint on /internal/v1/documents so no app ever holds bucket credentials. App: an `<app>_document_links` table in its own database holding (tenant_id, record_type, record_id, document_id, purpose) — the link is app-owned because only the app knows its records, and permission to see an attachment must be derived from the app's own read permission on the parent record, evaluated by the app. Register attachable record types and their allowed document types in app.yaml so the manifest validator can reject an app that invents its own storage. UI text must be everyday Indonesian ('Lampiran', 'Unggah foto'), not 'document reference'.

### [ ] `PLAT-03` — Shared master data has no owner, no contract, and no projection pattern — Procurement will mint its own vendor master

**Jenis:** missing-core-capability · **Verifikasi:** CONFIRMED · **Memblokir:** procurement, management-aset, core-reference-data

- **Dynamics 365:** In F&O there is exactly one VendTable, one InventTable, one UnitOfMeasure, one Currency/ExchangeRate, one DimensionAttribute set and one DirParty — every module joins them in the same database, so ownership is never a question. Financial dimensions and the vendor/product masters are shared platform data, not module data.
- **Keadaan sekarang:** Nothing exists and nothing is planned. No currency, exchange_rate, unit_of_measure, product, vendor, customer, or financial_dimension table anywhere in this repo or in app-erp-management-aset. Grep for currency\|uom\|unit_of_measure\|vendor\|supplier across apps/control-plane/database/migrations returns zero domain hits ('vendor' in docs means the software vendor). docs/dev only offers the reporting-projection pattern for cross-app reads (docs/dev/07-reporting-and-replicas.md:29-41) and a hierarchy projection example (docs/dev/08-query-scopes-and-schema.md:169-185), neither of which is a master-data ownership rule, and docs/dev/10-core-foundation-gates.md:19-20 gates both.
- **Bukti:** apps/control-plane/database/migrations/** — no currency/uom/product/vendor/dimension table (24 migrations, all listed). D:/Kerja/app-erp-management-aset/database/migrations/ — 3 migrations, asset master data only. docs/dev/08-query-scopes-and-schema.md:169-185 (projection example, hierarchy only). docs/dev/10-core-foundation-gates.md:19 ('Hierarchy projection ke module \| Belum').
- **Kenapa penting:** Procurement needs vendor, product/item, UoM, currency, tax code and delivery address on day one. Management Aset needs product/item (the asset's catalogue item), UoM and currency (acquisition value). Because there are no cross-app queries by design, whichever app declares vendor first owns it forever — and if Procurement owns vendor while Asset owns item, then Asset's 'asset acquired from vendor X' has no legitimate reference and someone will add a free-text vendor name. This is the failure mode that turns a deliberate architecture decision into a data-integrity defect, and it is unrecoverable after go-live.
- **Perubahan yang diperlukan:** Adopt one explicit pattern and enforce it in the manifest validator before app 2 is scaffolded. Recommendation: (a) Core owns the small, slow, cross-cutting reference data with no business process of its own — countries/regions, currencies and exchange rates, units of measure and conversions, financial dimensions, party/postal address (see PLAT-04). These get Core tables, a read API under /internal/v1/reference/*, and a `core.reference.<entity>.changed.v1` event. (b) Business masters with a real process behind them get exactly one owning app declared in a Core-held registry: vendor is owned by Procurement, product/item by an Inventory or Product app. (c) Every consumer app stores a read-only local projection table with an explicit `_projection` suffix (the naming convention docs/dev/08-query-scopes-and-schema.md:169 already uses), fed by the owner's event, carrying source_version and synced_at; a projection row may never be edited locally. (d) Enforcement points: extend app.yaml with `masterData: { owns: [...], consumes: [...] }`, validate in apps/control-plane/app/Http/Requests/Provider/AppCatalogRequest.php alongside the existing security/number_sequences blocks, reject registration of an app that declares ownership of an entity another app already owns, and add a CI contract test that fails if a migration creates a table whose name collides with a consumed entity without the projection suffix. Owner: Core (registry + reference data), owning app (master + events), consuming app (projection + inbox).

### [ ] `PLAT-05` — Business events, outbox and inbox are mandated by the design docs but implemented nowhere — and there is no broker

**Jenis:** doc-code-drift · **Verifikasi:** CONFIRMED · **Memblokir:** procurement, management-aset, core-workflow, core-notification, core-reference-data

- **Dynamics 365:** F&O's Business Events framework lets each module declare business events (VendorInvoicePostedBusinessEvent, PurchaseRequisitionWorkflowBusinessEvent, …), a tenant admin activates them per legal entity and binds each to an endpoint (Event Grid, Service Bus, webhook/HTTPS, Logic Apps), and the platform handles serialization, retry and dead-letter. Data events (create/update/delete on data entities) are available the same way.
- **Keadaan sekarang:** The docs mandate outbox as the only legal cross-database mechanism — 'Producer menyimpan payload ke outbox_events dalam transaksi yang sama dengan data bisnis' (docs/dev/04-api-and-integration.md:51), outbox_events/inbox_events appear in the target schema (docs/dev/08-query-scopes-and-schema.md:46-47), reliability rules require inbox dedupe and dead-letter (docs/dev/07-reporting-and-replicas.md:51-55), and app.yaml requires an asyncapi contract (docs/dev/02-module-standard.md:57-58). In code: no outbox_events or inbox_events table in any of the 24 Control Plane migrations, none in app-erp-management-aset's 3 migrations, no publisher worker, no consumer, no business_event registry, no endpoint/subscription table, no dead-letter table. app-erp-management-aset/contracts/asyncapi.yaml:4 is `channels: {}`. There is no broker in the deployment either: deploy/ contains only compose/README.md and web-shell.nginx.conf.example, and grep for kafka\|rabbit\|nats\|redis-stream\|EVENT_BROKER across config/ and .env.example returns nothing.
- **Bukti:** docs/dev/04-api-and-integration.md:51; docs/dev/08-query-scopes-and-schema.md:46-47; docs/dev/07-reporting-and-replicas.md:51-55; docs/dev/12-external-module-integration.md:69. Zero outbox/inbox table: grep -rn 'outbox' apps/control-plane/database/migrations D:/Kerja/app-erp-management-aset/database/migrations → nothing. D:/Kerja/app-erp-management-aset/contracts/asyncapi.yaml:4 'channels: {}'. deploy/ contains 2 files (find deploy -type f). No broker config: grep kafka\|rabbit\|nats\|EVENT_BROKER apps/control-plane/config apps/control-plane/.env.example deploy/ → zero.
- **Kenapa penting:** Every other fix in this audit assumes eventing: workflow completion (PLAT-01), master-data projections (PLAT-03), address changes (PLAT-04), alerts (PLAT-07), reporting projections. Because nothing exists, the very first cross-app requirement will be met with a synchronous REST call inside a database transaction — which is the exact distributed-transaction failure the split-database design was chosen to avoid. The number-sequence design already depends on an app-side outbox worker (docs/dev/14-number-sequences.md:111,171) that no app has implemented, so continuous sequences would leak reservations today.
- **Perubahan yang diperlukan:** Three pieces, all needed before app 2. (1) Shared package (this is the legitimate second consumer that docs/dev/02-module-standard.md:107 requires before creating a package): a published coreerp/app-kernel providing the outbox table migration, the transactional write helper, the publisher worker with backoff + dead-letter, the inbox/processed_events dedupe store, and the standard envelope from docs/dev/04-api-and-integration.md:36-47 including correlation_id. (2) Core: a business_event registry populated from each app's asyncapi contract at catalog registration (same place as permissions in apps/control-plane/app/Actions/Provider/RegisterAppCatalog.php:25-55), plus tenant-facing subscription/endpoint configuration with signature secret, retry policy and a visible dead-letter list — a tenant admin must be able to see 'kiriman gagal' and retry it. (3) Deployment: choose and add one broker to deploy/compose (Redis Streams is sufficient for pooled and survivable on-prem; Kafka is not justified yet) and record the choice as an ADR, because on-prem perpetual must run it locally with no vendor connection.

### [ ] `PLAT-04` — No party model and no postal address at all — every address in the product has nowhere to live

**Jenis:** missing-core-capability · **Verifikasi:** ADJUSTED · **Memblokir:** procurement, management-aset, core-party, core-reference-data

- **Dynamics 365:** F&O's Global Address Book is platform-level: DirPartyTable (party with type Person/Organization), DirPartyLocation linking a party to LogisticsLocation, LogisticsPostalAddress (effective-dated, with country/region, state, county, city, district, street, ZIP/postcode, and a per-country address format that controls field order and which fields are mandatory), address purposes/roles (Invoice, Delivery, Business, Home, Payment, one primary per purpose), LogisticsElectronicAddress for contact info (phone/e-mail/URL/telex, with purpose and one primary), and name affixes/sequence. Vendor, customer, worker, warehouse, legal entity and asset location are all DirParty-backed, so one address change propagates everywhere.
- **Keadaan sekarang:** Nothing. There is no party, party_type, location, postal_address, address_purpose, contact_info, or name_affix table anywhere. The only address-shaped column in the entire platform is legal_entities.country_code char(2) with no countries table and no foreign key. Grep for postal_address\|addresses\|party across apps/control-plane/database, apps/control-plane/app and docs/dev returns zero hits — and the D365 reference document the team already researched (docs/references/dynamics-365-organization-model.md) does not cover the Global Address Book either, so the ORG auditor cannot have covered it.
- **Bukti:** apps/control-plane/database/migrations/2026_07_20_000000_create_core_identity_access_tables.php:43-48 (legal_entities: organization_id, company_code, country_code char(2), timestamps — nothing else; no registration or tax data despite docs/dev/01a-tenant-and-org-hierarchy.md:53 claiming 'registration/tax data'). grep -rn -i 'postal_address\|addresses\|party' apps/control-plane/database apps/control-plane/app docs/dev → zero hits. grep -rn -i 'global address book\|party\|postal\|address' docs/references/dynamics-365-organization-model.md → zero hits.
- **Kenapa penting:** Asset needs a physical location address per asset and per site. Procurement needs vendor addresses, a delivery address on the PO, and an invoice address distinct from it — that is three address purposes on one party before the app has any features. Without a Core party/address model each app stores free-text addresses; a vendor whose address changes then has stale addresses in every app, statutory documents print the wrong address, and there is no way to ever reconcile them. This also silently blocks anything statutory: Indonesian tax documents require a structured NPWP-bearing address on both parties.
- **Perubahan yang diperlukan:** Core-owned, new domain in the Control Plane, sequenced immediately after workflow because Procurement needs vendor addresses in its first release. Tables: parties (tenant_id, party_type person\|organization, name, plus name affix/sequence fields), party_locations (party → location, purposes as a set, is_primary_per_purpose), postal_addresses (effective-dated with valid_from/valid_until so history is preserved, country_region_code FK, state/province, city, district, street, postcode, and a `formatted` cache), electronic_addresses (type phone\|email\|url, purpose, is_primary), address_purposes (seeded: Tagihan, Pengiriman, Bisnis, Pembayaran — Indonesian labels per rule 6). legal_entities and any future vendor/customer/worker record must reference a party_id rather than duplicating address columns. Expose read + resolve via /internal/v1/parties and emit core.party.address-changed.v1 so consuming apps can refresh projections. Also add the registration/tax fields that docs/dev/01a-tenant-and-org-hierarchy.md:53 already claims exist on legal entities but do not.
- **Koreksi verifier:** The gap is real but the framing and severity are wrong. What is missing and foundational is (a) an owner decision for party/address, and (b) the country/region reference table that any address format, postcode rule or statutory behaviour must key off (which is really PLAT-13). A full Core-owned DirParty clone is NOT a forced conclusion in a split-database architecture: F&O centralises DirParty because every module shares one database, whereas here 'vendor address is owned by the app that owns the vendor master' is an equally defensible design and is cheaper. Prescribing a Core party domain as a blocker over-constrains the owner. Procurement can ship its first release with an app-owned vendor address provided the ownership decision from PLAT-03 is recorded first — which is why this is high, not blocker, and why it should be merged into the PLAT-03 ownership decision rather than sequenced as its own Core release unit. Separately and independently real: legal_entities is missing the registration/tax attributes its own design doc claims it has.

### [ ] `PLAT-08` — No tenant-facing batch and recurring job framework — Laravel queues are developer infrastructure, not an ERP batch framework

**Jenis:** missing-core-capability · **Verifikasi:** CONFIRMED · **Memblokir:** management-aset, procurement, core-batch, core-notification

- **Dynamics 365:** In F&O a legal entity carries an accounting currency, a reporting currency, an exchange-rate type and registration/tax identifiers; every amount posted anywhere resolves its currency through the legal entity, and statutory documents print the registration numbers from it.
- **Keadaan sekarang:** legal_entities is organization_id (PK), company_code, country_code char(2), timestamps, plus fiscal_calendar_id added later. There is no accounting_currency, no reporting_currency, no exchange-rate concept, and no registration or tax identifier — despite docs/dev/01a-tenant-and-org-hierarchy.md listing 'registration/tax data' as part of the table and docs/dev/15-fiscal-calendars.md asserting that a legal entity owns 'konsekuensi legal, ledger, pajak, mata uang, dan kalender fiskal'. Only the fiscal-calendar half of that sentence was built.
- **Bukti:** apps/control-plane/database/migrations/2026_07_20_000000_create_core_identity_access_tables.php:43-47 (full table definition); apps/control-plane/database/migrations/2026_07_26_010000_create_fiscal_calendar_tables.php:43-45 (only fiscal_calendar_id added since); docs/dev/01a-tenant-and-org-hierarchy.md 'legal_entities: organization_id, tenant_id, company_code, country_code, registration/tax data'; docs/dev/15-fiscal-calendars.md 'Pemilik kebenaran'; grep for currency across all 23 migrations returns zero hits.
- **Kenapa penting:** This is narrower and more immediately actionable than the general master-data finding, and it bites both named apps in their first real increment: Management Aset records an acquisition value and Procurement records a purchase price, and neither has a defined currency to record it in — so each app will add its own currency column or, worse, assume IDR implicitly, and a multi-currency or multi-entity customer becomes a data migration. It is also the anchor for exchange rates and for any Indonesian statutory output (NPWP on the issuing party). Unlike a full party model this is a few columns plus a small currencies reference table, and it is unambiguously Core-owned because legal entity is Core-owned.
- **Perubahan yang diperlukan:** Add accounting_currency (FK to a new Core currencies reference table seeded with ISO 4217 codes and Indonesian names) plus the registration/tax identifier fields the design doc already claims, to legal_entities; make accounting_currency required on the legal-entity creation path (apps/control-plane/app/Http/Requests/Organization/OrganizationRequest.php and CreateOrganization); expose currency and registration data through the reference read API so apps format and print amounts consistently rather than each inventing a currency column. Sequence exchange_rates after currencies, before the first multi-currency requirement. Owner: Core.

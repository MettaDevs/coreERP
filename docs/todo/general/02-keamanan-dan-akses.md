## Blocker

### [ ] `SEC-01` — No authorization contract: a business app can never ask Core "may this user do X on org Y"

**Jenis:** contract-gap · **Verifikasi:** CONFIRMED · **Memblokir:** management-aset, procurement, any-future-app, record-level-security, field-level-security

- **Dynamics 365:** In D365 F&O, authorization is enforced by the platform kernel at the entry point (SysSecurityRuntime / AOS), not by the module. A module declares menu items and privileges; the runtime decides allow/deny and applies XDS. The module never has to be trusted with the decision.
- **Keadaan sekarang:** Core exposes no authorization endpoint. `routes/web.php` has launch-manifest, workspace-context, roles, memberships, organizations, number-sequences, invitation-codes, provider/* — nothing like `POST /api/v1/authorize` or `GET /api/v1/effective-permissions`. `routes/api.php` (the app-facing surface) exposes only four number-sequence endpoints. Enforcement happens entirely inside the app, from a `permissions[]` array it read out of a token it verified with a shared secret.
- **Bukti:** apps/core/routes/web.php:140-170 (no authorization endpoint); apps/core/routes/api.php:6-11 (app-facing surface is number sequences only); D:/Kerja/app-erp-management-aset/api/app/Http/Controllers/MasterDataController.php:199-204 (the app is the only enforcer); D:/Kerja/app-erp-management-aset/app.yaml:49-203 (36 permissions + 8 duties declared, enforced by nobody in Core)
- **Kenapa penting:** Management Aset declares 36 permissions and 8 duties in app.yaml. Core registers them, lets tenants compose roles from them, and then hands the app a list of strings and hopes. A buggy or malicious app version silently grants everything: skip `requirePermission()` and Core cannot tell. There is also no way for an app to answer org-level questions at all — the token has no scope set — so record-level authorization is not merely unenforced, it is unaskable. Every future app must reimplement the check from scratch, and Core has no way to prove any app did.
- **Perubahan yang diperlukan:** Core owns a signed authorization contract: (a) `POST /internal/v1/authorize` taking {user_id\|context_token, app_id, permission_code, organization_id} returning allow/deny + reason + correlation_id, expanding role→duty→privilege→permission AND applying role_assignment_org_scopes/closure; (b) `GET /internal/v1/effective-access` returning permissions grouped by permitted organization id set, so an app can build an org filter; (c) a shared middleware in app-erp-template that calls it with a short local cache and fails closed. Owner: Core (contract + endpoint), app template (client middleware).

### [ ] `SEC-02` — One global symmetric signing key for all app context tokens — any app can forge tenant context and other apps' tokens

**Jenis:** wrong-model · **Verifikasi:** CONFIRMED · **Memblokir:** management-aset, procurement, tenant-isolation, on-prem-packaging

- **Dynamics 365:** D365 F&O never hands a module a bearer of its own authority. Service-to-service uses Entra ID with per-application registrations and asymmetric signing; the token issuer's private key is never distributed to resource servers.
- **Keadaan sekarang:** `AppContextToken::issue()` HMAC-SHA256s the payload with `config('coreerp.app_context_signing_key')`, a single value from `COREERP_APP_CONTEXT_SIGNING_KEY`. The app verifies with the same key (`config('services.coreerp.context_signing_key')`). Symmetric means the verifier is also a signer. There is no `kid`, no per-app key, no per-tenant key, no `jti`, and no revocation list. `aud` is checked only by the receiving app against its own config, which the forging app also controls.
- **Bukti:** apps/core/app/Support/AppContextToken.php:18-37; apps/core/config/coreerp.php:16; apps/core/.env.example:77; D:/Kerja/app-erp-management-aset/api/app/Http/Middleware/RequireCoreErpContext.php:30-40
- **Kenapa penting:** Directly answers "can an app forge the tenant context?" — yes, trivially. With the verify key, Management Aset can mint a token with any `tenant_id`, any `permissions[]`, and `aud: procurement`, and Procurement will accept it as authentic Core output. A single leaked env var (CI log, container image, on-prem installer) is a platform-wide forgery capability across every tenant and every app, not a scoped compromise. This also makes the on-prem story unshippable: the customer's own operators would hold the key that mints authority over the vendor's SaaS estate if any key is ever reused.
- **Perubahan yang diperlukan:** Switch to asymmetric signing: Core holds an Ed25519/RS256 private key, publishes `GET /internal/v1/jwks` with `kid`, apps verify public-key-only. Add `jti` + `nonce` and a Core-side short-TTL replay cache, and per-app `aud` bound to the credential that requested the token. Rotate keys with overlapping `kid`. Owner: Core (issuer + JWKS), app template (verifier).

### [ ] `SEC-04` — Organization scope is stored and pinned but enforced in exactly one query — every listing endpoint and every app ignores it

**Jenis:** missing-core-capability · **Verifikasi:** ADJUSTED · **Memblokir:** management-aset, procurement, record-level-security, org-scope-ui-honesty

- **Dynamics 365:** D365 F&O role assignments carry "Assign organizations" (Grant/Revoke, with or without children on a chosen hierarchy), and the runtime applies it to data access, not just to the legal-entity switcher.
- **Keadaan sekarang:** `role_assignment_org_scopes` rows are written by three actions and read by one: `CurrentWorkspace::organizations()`, used only by the workspace selector. `GET /api/v1/organizations` and `settings/organization` return every organization in the tenant. `settings/access` returns every organization and every member. The context token carries only the single selected `legal_entity_id`/`org_unit_id`, never the scope set or `include_descendants`, so an app has nothing to filter on — and Management Aset in fact never reads either value: its `tenantQuery()` filters on `tenant_id` alone.
- **Bukti:** apps/core/app/Support/CurrentWorkspace.php:51-73 (the only enforcement); apps/core/app/Http/Controllers/Organization/OrganizationController.php:25-34 (unscoped list); apps/core/app/Http/Controllers/Access/AccessController.php:61-70 (unscoped list); apps/core/app/Support/AppContextToken.php:24-34 (no scope claim); D:/Kerja/app-erp-management-aset/api/app/Http/Controllers/MasterDataController.php:176-181 (tenant_id only)
- **Kenapa penting:** This is the answer to "is scope actually applied to any query, or only stored?" — stored, plus one query. A user scoped to Branch Makassar picks Makassar in the header, then Management Aset serves them every asset row in the tenant, because the app has no org column and no org claim. The org scope UI therefore promises a boundary that does not exist below the selector. Doc claim `docs/dev/09-identity-and-access.md:90` ("Effective access adalah gabungan seluruh assignment aktif setelah organization scope diterapkan") and acceptance target line 232 ("API tetap menolak akses walaupun ... workspace selector dimanipulasi") are not met for any business data.
- **Perubahan yang diperlukan:** (a) Add a reusable `OrganizationScopeQuery` in Core and apply it to `OrganizationController::index`, `AccessController::index`, and any org-returning API; (b) add an `organizations` claim (explicit resolved id list, or scope descriptor) to the context token, or expose it via the SEC-01 effective-access endpoint; (c) require transactional app tables to carry `legal_entity_id`/`org_unit_id` in the app contract and have the app template filter on the granted set. Owner: Core (query + claim + contract), each app (column + filter).
- **Koreksi verifier:** Confirmed that org scope is written by three actions, read by exactly one query (the workspace selector), and carried by no token claim, so no app can filter records by organization. One correction to the illustration: management-aset today holds only master/reference data (kondisi aset, group aset, kategori aset), which is legitimately tenant-wide in D365 too — so 'the app serves them every asset row' overstates today's exposure. The correct statement of harm is forward-looking and still blocker-grade: the first transactional table (asset register, purchase order) will be designed without an org column and without a scope claim to filter on, because neither the app contract nor the token requires one. Also note CurrentWorkspace.php:47 — any owner/admin bypasses scope entirely, so the boundary can never constrain an administrator.

## Tinggi

### [ ] `SEC-03` — The only endpoint that mints app service credentials creates an unscoped cross-tenant credential

**Jenis:** doc-code-drift · **Verifikasi:** ADJUSTED · **Memblokir:** tenant-isolation, number-sequence-integrity, management-aset, procurement

- **Dynamics 365:** D365 F&O service principals are registered per environment/tenant; a credential is never implicitly valid across customer tenants.
- **Keadaan sekarang:** Migration 2026_07_26_040000 added `tenant_id` to `app_service_credentials` specifically to stop one leaked token issuing numbers for every tenant, and its own docblock says "New credentials should be scoped." But `AppServiceCredentialController::store()` never writes `tenant_id` — it is the only creation path in the codebase, and it always produces the null-tenant, works-for-any-tenant variant. `AuthenticateAppService` explicitly accepts `whereNull('tenant_id')`. A test locks the unscoped behaviour in as intended.
- **Bukti:** apps/core/app/Http/Controllers/Provider/AppServiceCredentialController.php:15-28 (no tenant_id, no tenant in validation rules); apps/core/app/Http/Middleware/AuthenticateAppService.php:26-30; apps/core/database/migrations/2026_07_26_040000_scope_app_service_credentials_to_tenant.php:8-12 (stated intent); apps/core/tests/Feature/ControlPlane/NumberSequenceTest.php:226-243 (`test_an_unscoped_credential_still_works_for_an_entitled_tenant`)
- **Kenapa penting:** The mitigation exists in schema and is proven by a test, then defeated by the only code path that uses it. Every credential in any real deployment is cross-tenant. Combined with SEC-02 (shared context key), an app compromise is a whole-estate compromise on both the app→Core and Core→app directions. The `test_a_tenant_scoped_credential_cannot_issue_numbers_for_another_tenant` test passes only because the test constructs the scoped row by hand — no production code ever does.
- **Perubahan yang diperlukan:** Require `tenant_id` in `AppServiceCredentialController` (validated against an active entitlement for that app), add a migration to backfill/expire existing null rows, then drop the `whereNull('tenant_id')` branch from `AuthenticateAppService` and delete the test that blesses it. Add credential rotation and revocation endpoints. Owner: Core.
- **Koreksi verifier:** The gap is real and stated correctly, but the severity is wrong for this rubric. This does not stop management-aset or procurement from being built, and it does not push either app toward a wrong design — it is a live cross-tenant authentication hole on Core's own internal API that stops the platform going to production. Severity is high, not blocker. The finding should also state the aggravating detail: the tenant identity on the internal API comes from an unauthenticated request header, so the null-tenant credential is not merely 'valid for all tenants' — it lets the holder assert any tenant it likes.

### [ ] `SEC-05` — No access audit trail: no allow/deny events, no correlation ID, no trusted actor

**Jenis:** missing-core-capability · **Verifikasi:** CONFIRMED · **Memblokir:** compliance-readiness, provider-access-governance, temporary-access, sod

- **Dynamics 365:** D365 F&O user security governance records role assignment changes, temporary access grants, privileged-access sessions and SoD overrides, each with actor and timestamp; the platform carries an activity/correlation id end to end.
- **Keadaan sekarang:** Absent. The only audit table in the repo is `number_sequence_audit_events`, scoped to number issuance, with a nullable `user_id` and no correlation id. No table, model, listener, or middleware records role assignment changes, invitation creation/redemption, membership changes, workspace switches, provider actions, or authorization denials. A repo-wide search for `access_audit`, `audit_event`, `correlation` outside the number-sequence feature returns nothing.
- **Bukti:** apps/core/database/migrations/2026_07_24_030000_create_number_sequence_tables.php:132-145 (only audit table; no correlation_id, nullable user_id); verified absent: no migration, model, or class matching access_audit/audit_event/correlation elsewhere in apps/core; doc claims it as target at docs/dev/09-identity-and-access.md:145,182 and gate table docs/dev/10-core-foundation-gates.md:18
- **Kenapa penting:** `UpdateMembership` deletes all of a member's role assignments and recreates them (app/Actions/Access/UpdateMembership.php:42-51) leaving no trace of what was removed, by whom, or when. An admin can grant themselves every duty, act, and revert, and nothing in the system remembers. Doc line 182 asserts "Semua perubahan assignment menghasilkan audit event" — false. Without a correlation id, an authorization denial in an app cannot be tied to the Core decision that produced it, which also makes SEC-01 unverifiable after the fact.
- **Perubahan yang diperlukan:** Create `access_audit_events` (tenant_id, correlation_id, actor_user_id, actor_kind [user\|provider\|app\|system], action, subject_type, subject_id, before/after json, organization_id, ip, occurred_at) with append-only semantics and a retention setting. Emit from every Access action, invitation create/redeem, workspace activation, provider action, and every authorize decision from SEC-01. Propagate `X-CoreERP-Correlation-Id` through AuthenticateAppService and the context token. Owner: Core.

### [ ] `SEC-08` — Workforce absent: no workers, jobs, positions, position assignments, hierarchy types, or position relationships

**Jenis:** missing-app · **Verifikasi:** ADJUSTED · **Memblokir:** automatic-role-assignment, approval-routing, sod-by-position, management-aset, procurement, signing-limits, delegation

- **Dynamics 365:** D365 F&O separates department (operating unit), job, position, and worker-position assignment; position relationships form managerial and matrix reporting hierarchies independent of the organization hierarchy; positions drive automatic role assignment, approval routing, and signing limits.
- **Keadaan sekarang:** Absent. No `workers`, `jobs`, `positions`, `worker_position_assignments`, `position_hierarchy_types`, or `position_relationships` table exists in any migration. A repo-wide search finds only unrelated hits (queue "worker", fiscal "position"). Identity stops at `users` + `tenant_memberships`; there is no concept of a person occupying a seat.
- **Bukti:** Verified absent across apps/core/database/migrations (24 files, none creating workforce tables); only matches for worker/position are apps/core/app/Console/Commands/RunNumberSequenceLoad.php:15-56 (queue workers) and apps/core/app/Actions/FiscalCalendar/FiscalCalendarService.php:113 (fiscal position); declared as target at docs/dev/09-identity-and-access.md:92-104,123-128 and docs/references/dynamics-365-organization-model.md:115-133,263
- **Kenapa penting:** Concretely blocked: (1) automatic role assignment has no business fact to trigger on (SEC-10) — every grant stays manual forever; (2) approval routing has no reporting line, so Procurement cannot route a requisition to "my manager"; (3) SoD by position is impossible — conflicts can only be evaluated per login identity, so splitting duties across two seats held by one person is invisible; (4) Management Aset has no custodian: an asset cannot be assigned to a position, only to a login, so a staff change orphans every asset; (5) requisitioner/on-behalf-of is unrepresentable. Doc acceptance "user dengan dua position menerima union role yang tepat tanpa identity ganda" (line 225) has no data model behind it.
- **Perubahan yang diperlukan:** Stand up a workforce owner. Given the one-repo-per-app rule this is an HR/Personnel business app owning `workers`, `jobs`, `positions`, `worker_position_assignments`, `position_hierarchy_types`, `position_relationships`, publishing position/assignment events via AsyncAPI. Core must own only the link Core needs: `membership_id ↔ worker_id`/`position_id` reference plus the event subscription that feeds automatic role assignment. Decide and document this boundary before either app is built. Owner: new HRD app (facts) + Core (link + rule evaluation).
- **Koreksi verifier:** The absence is confirmed and high severity is right, but the framing overstates novelty and one consequence. This is docs/dev/10's own top-listed gate with the owner already assigned to an HRD app, so the auditor's 'decide and document this boundary before either app is built' is already done at the doc level; what is actually missing is the Core-side link (membership_id ↔ worker_id/position_id) and the event subscription, which no doc or migration specifies. The 'Management Aset has no custodian, so a staff change orphans every asset' consequence is forward-looking only — management-aset currently has no asset register at all, only eight master/reference tables (D:/Kerja/app-erp-management-aset/database/migrations, 3 migrations). Keep high: it genuinely gates approval routing, signing limits, and automatic assignment for procurement.

### [ ] `SEC-12` — Core's own access-administration reads are ungated: any tenant member can enumerate every member, role, email, and last login

**Jenis:** missing-core-capability · **Verifikasi:** ADJUSTED · **Memblokir:** tenant-data-privacy, access-model-confidentiality

- **Dynamics 365:** D365 F&O gates the System administration → Users and Security configuration forms behind security roles; reading the user roster and role assignments is itself a privileged operation.
- **Keadaan sekarang:** `settings/access` sits behind `auth` only. `AccessController::index` computes `canManage` and passes it to the UI for button-hiding, but never aborts — it returns every membership with name, email, last_login_at, active roles, role_ids and org scope, plus every role, organization, hierarchy, and every invitation. `GET /api/v1/roles` (`RoleController::index`) and `GET /api/v1/memberships/{id}` (`MembershipController::show`) check tenant identity but not `manage-access`. `GET /api/v1/organizations` is likewise ungated. Write paths are correctly gated (RoleRequest/MembershipRequest/InvitationRequest `authorize()`, `UpsertRole`/`UpdateMembership`/`CreateInvitation` re-check `canManageAccess()`), so this is a read-side gap.
- **Bukti:** apps/core/routes/web.php:104 and :144-147 and :147 (auth only, no can: middleware); apps/core/app/Http/Controllers/Access/AccessController.php:19-31 (no abort, canManage is presentational); apps/core/app/Http/Controllers/Access/RoleController.php:15-24 and :33-38 (no gate); apps/core/app/Http/Controllers/Organization/OrganizationController.php:25-34 (no gate)
- **Kenapa penting:** docs/dev/09-identity-and-access.md:47 states the rule this violates: "UI menyembunyikan action yang tidak dimiliki user, tetapi API tetap memvalidasi authorization." Here the UI hides and the API does not validate. A plain `user` member — including one onboarded through a scoped invitation — can `GET /api/v1/roles` and `/api/v1/memberships/{id}` to map the tenant's entire access model, and `GET /settings/access` to harvest every colleague's email and last-login. That is reconnaissance for exactly the escalation paths described in SEC-04 and SEC-15, and a privacy exposure independent of any escalation.
- **Perubahan yang diperlukan:** Add `->middleware('can:manage-access')` to settings/access, api/v1/roles (index/show), api/v1/memberships/{id}, and api/v1/organizations, or abort in each controller as `IdentityMonitorController` already does. Then narrow the payloads: a non-manager who legitimately needs a member list should get names only, not emails, last-login, role_ids, or invitation state. Add tests for each. Owner: Core.
- **Koreksi verifier:** Confirmed and under-scoped — the auditor missed two more ungated reads. Add: `GET /api/v1/invitation-codes` (apps/core/app/Http/Controllers/Access/InvitationCodeController.php:15-24) returns every invitation code record with its roles to any tenant member, and `GET /api/v1/number-sequences` (apps/core/app/Http/Controllers/NumberSequence/NumberSequenceController.php:19-34) returns the tenant's whole number-sequence configuration to any member, while its update path is correctly gated by NumberSequenceSettingsRequest.php:11-14. So the read-side gap is six endpoints, not four. Also worth stating plainly: the `manage-access` Gate is defined and used only inside FormRequest::authorize() — it is applied to zero routes.

### [ ] `SEC-14` — Enterprise authentication missing: no SSO/OIDC/SAML, no SCIM, no per-tenant MFA or session policy, no service accounts, no token-auth API

> **Sebagian sudah dikerjakan sejak temuan ini ditulis.** SSO OIDC berdiri sejak 13 September 2026 di
> Core dan di admin.erp — authorization code + PKCE, identitas ditautkan lewat `iss`+`sub`, undangan
> terikat subjek, dan back-channel logout; lihat [SSO](/dev/32-sso). Yang **masih** kosong dari butir
> ini: SCIM, kebijakan MFA dan sesi per tenant, service account, dan API ber-token.

**Jenis:** missing-core-capability · **Verifikasi:** ADJUSTED · **Memblokir:** enterprise-sales, integration-apis, tenant-security-policy, offboarding-hygiene

- **Dynamics 365:** D365 F&O delegates identity to Microsoft Entra ID: federated SSO, conditional access and MFA policy owned by the customer tenant, group-based provisioning, and OAuth service principals for machine access. The ERP itself stores no passwords.
- **Keadaan sekarang:** Local passwords only, via Fortify: registration, password reset, email verification, TOTP two-factor (`confirm: true`), and passkeys/WebAuthn. Composer requires no Socialite, SAML, OIDC, Sanctum or Passport. 2FA is opt-in per user with no tenant-level enforcement (no column, no policy check, no middleware requiring `two_factor_confirmed_at`). Session lifetime is one global `SESSION_LIFETIME`, not per tenant. There are no tenant service accounts, and `api/v1` routes are declared inside `routes/web.php`, so they inherit the web group and require a session cookie plus CSRF — there is no bearer-token path for a tenant user or external integration.
- **Bukti:** apps/core/composer.json:11-19 (Fortify only; no socialite/saml/oidc/sanctum/passport); apps/core/config/fortify.php:169-189 (features: registration, resetPasswords, emailVerification, twoFactorAuthentication, passkeys); apps/core/app/Models/User.php:38-41; apps/core/config/session.php:35 (single global lifetime); apps/core/routes/web.php:140-170 (api/v1 inside the web group)
- **Kenapa penting:** What exists (passkeys + TOTP + strong production password policy at app/Providers/AppServiceProvider.php:73-81) is a solid consumer-grade baseline and better than many ERPs. What is missing is what makes an enterprise able to buy it: a customer with Entra ID or Google Workspace cannot federate, cannot enforce MFA centrally, cannot deprovision a leaver in one place (SCIM), and their security team cannot approve a system that holds a second password for every employee. The session+CSRF-only API also means no external integration and no tenant automation is possible at all — and since business apps are the only permission enforcers (SEC-01), there is no machine identity model for them to act on a user's behalf either.
- **Perubahan yang diperlukan:** Add per-tenant identity provider configuration (OIDC first, SAML second) with domain-based routing and JIT membership creation mapped to roles; add SCIM 2.0 user/group provisioning; add a per-tenant security policy (MFA required, session lifetime, idle timeout, IP allowlist) enforced in middleware; add tenant-scoped service accounts / OAuth clients; move `api/v1` to a real API group with token auth (Sanctum or OAuth) and keep the Inertia routes separate. Sequence: token-auth API and per-tenant MFA policy first (cheap, unblocks integrations), then OIDC, then SCIM. Owner: Core.
- **Koreksi verifier:** The missing-enterprise-auth gap is confirmed (no SSO/OIDC/SAML, no SCIM, no per-tenant MFA or session policy, no tenant service accounts, no token-auth API — api/v1 is session+CSRF only). But the current_state overstates the working baseline: email verification is configured in Fortify and inert in practice, because User does not implement MustVerifyEmail. The honest baseline is local password + TOTP + passkeys + a production password policy, with email ownership never proven. High severity stands.

### [ ] `SEC-15` — One org scope row per assignment, and the UI applies a single scope to every role at once — per-role organization assignment is unreachable

**Jenis:** wrong-model · **Verifikasi:** ADJUSTED · **Memblokir:** org-scope-correctness, cross-app-roles, management-aset

- **Dynamics 365:** D365 F&O "Assign organizations" is per role assignment, and one assignment can grant multiple organizations, each independently with or without children, plus explicit revoke entries.
- **Keadaan sekarang:** `role_assignment_org_scopes` has `unique('assignment_id')`, so an assignment can hold at most one organization. Worse, `UpdateMembership` resolves ONE scope from the request and writes that same scope to every role it creates for the member, and the read side (`AccessController`) displays only `roleAssignments->first()?->organizationScope`. The request payload has a single `organization_id`/`hierarchy_id`/`include_descendants` triple for the whole membership.
- **Bukti:** apps/core/database/migrations/2026_07_20_010000_add_organization_structure_and_closure.php:78 (unique per assignment); apps/core/app/Actions/Access/UpdateMembership.php:36,43-51 (one scope, all roles); apps/core/app/Http/Controllers/Access/AccessController.php:32-47 (reads first assignment's scope only); apps/core/app/Http/Requests/Access/MembershipRequest.php:56-65 (single scope triple)
- **Kenapa penting:** The flagship scenario in CoreERP's own docs — the Finance person who also controls assets (docs/dev/09:43) — cannot be scoped correctly: Finance Manager for the whole company plus Asset Controller for Makassar only is unrepresentable, and granting a role for two branches requires either two memberships or widening to the whole tenant. Because the read side shows only the first assignment's scope, an admin editing a member with divergent scopes (creatable via the invitation path with different roles) will unknowingly overwrite all of them with whatever the form displayed. That is silent privilege change through the admin UI.
- **Perubahan yang diperlukan:** Drop `unique('assignment_id')` in favour of `unique(assignment_id, organization_id, hierarchy_id)` with an explicit grant/revoke flag; move the scope triple into the per-role structure of the membership payload; render and edit scope per role in the UI (everyday Indonesian, e.g. "berlaku untuk" per tanggung jawab). Add a test that divergent per-role scopes survive an unrelated membership edit. Owner: Core.
- **Koreksi verifier:** Confirmed exactly as described, but medium understates it. Two things push this to high. First, the read side shows only the first assignment's scope while the write side overwrites all of them, so an admin who opens and saves a member created through the invitation path with divergent per-role scopes silently rewrites every scope to whatever the form happened to display — that is unlogged privilege change through the normal admin UI (and unlogged because SEC-05 means nothing records it). Second, the fix is a schema change to role_assignment_org_scopes plus a payload contract change; doing it after apps start consuming an org-scope claim (SEC-04) is rework. Both fit 'needs rework or cannot go to production'.

### [ ] `SEC-21` — No membership lifecycle: a tenant member can never be deactivated, removed, or have ownership transferred — `tenant_memberships.status` has readers but no writer

**Jenis:** missing-core-capability · **Verifikasi:** VERIFIER-FOUND · **Memblokir:** offboarding-hygiene, tenant-continuity, compliance-readiness, access-model-confidentiality

- **Dynamics 365:** D365 F&O user administration supports disabling a user account, setting an account expiry date, and removing role assignments independently; offboarding a leaver is a first-class operation, and system administrator responsibility can be reassigned.
- **Keadaan sekarang:** `tenant_memberships.status` is created at apps/core/database/migrations/2026_07_20_000000_create_core_identity_access_tables.php:61 with default 'active', and it IS read as an authorization input — apps/core/app/Support/CurrentWorkspace.php:27 filters memberships on `status='active'`, apps/core/app/Models/TenantMembership.php:45 requires `status==='active'` for canManageAccess(), and apps/core/app/Http/Controllers/Organization/WorkspaceContextController.php:20 filters on it. There is no DELETE route for memberships (apps/core/routes/web.php:145-146 exposes only show and update). And apps/core/app/Actions/Access/UpdateMembership.php:23,26-30 forbids both editing an owner other than yourself and moving the owner role at all, so there is no ownership transfer path either.

- **Kenapa penting:** Offboarding is the single most common access-governance operation in any ERP and it is unimplementable. The best an admin can do is demote to `user` and set role_ids to [] — the person keeps an active membership, keeps logging in, keeps the tenant in their workspace switcher, and (because of SEC-12) can still enumerate every colleague's email, last login, and the tenant's entire role model. Nothing records that it happened (SEC-05). Worse, if the sole owner leaves the company the tenant is permanently stuck: no one can become owner and no one can remove the departed owner's access. The status column looks like the capability exists, which is exactly the failure mode docs/dev/10-core-foundation-gates.md rule 3 warns against ('writer, reader, failure state, dan test').
- **Perubahan yang diperlukan:** Add a membership lifecycle to Core: PATCH status (active\|suspended) and DELETE (or status='removed') on `/api/v1/memberships/{id}`, gated on manage-access, with the owner protected and a required reason; add an explicit ownership-transfer action that demotes the outgoing owner in the same transaction; invalidate the user's sessions and any outstanding context tokens on suspend/remove (ties to SEC-17); emit the change to the audit trail (SEC-05). Add a test that a suspended member gets 403 on every tenant endpoint. Owner: Core.

### [ ] `SEC-22` — Core's own administration authority is a three-value `system_role` outside the security chain, and it is a blanket, unscopeable bypass of organization scope

**Jenis:** wrong-model · **Verifikasi:** VERIFIER-FOUND · **Memblokir:** org-scope-correctness, delegated-administration, tenant-data-privacy, org-scope-ui-honesty

- **Dynamics 365:** D365 F&O governs System administration itself with security roles (System administrator, Security administrator, IT manager), composed of duties and privileges like any other role, and those assignments can carry organization scope. Administrative authority is expressible at the same granularity as business authority.
- **Keadaan sekarang:** Tenant administration is decided entirely by `TenantMembership::canManageAccess()` (apps/core/app/Models/TenantMembership.php:43-46), which is `status==='active' && system_role in ['owner','admin']`. `system_role` is a bare string(20) column (migration :60) constrained only in request validation (MembershipRequest.php:20, Rule::in(['user','admin','owner'])). It is never expressed as duties, privileges, or permissions, so it cannot be composed, cannot be split, and cannot be scoped. Critically, apps/core/app/Support/CurrentWorkspace.php:47 returns every organization in the tenant for anyone who passes canManageAccess(), before any scope resolution runs — so the entire role_assignment_org_scopes model is inert for owners and admins by construction. The same all-or-nothing flag governs creating organizations, publishing hierarchy versions, composing roles, editing every membership, minting invitations, and configuring number sequences (grep canManageAccess: 8 call sites across Actions and Controllers).
- **Bukti:** apps/core/app/Models/TenantMembership.php:43-46; apps/core/app/Support/CurrentWorkspace.php:44-49 (canManageAccess short-circuits organizations() before scope is read at :51); apps/core/database/migrations/2026_07_20_000000_create_core_identity_access_tables.php:60 (system_role string(20), no enum); apps/core/app/Actions/Access/UpsertRole.php:17, UpdateMembership.php:21, CreateInvitation.php:25, Organization/CreateOrganization.php:17, CreateOrganizationHierarchy.php:19, PlaceOrganizationInHierarchy.php:17, PublishOrganizationHierarchy.php:15 (all the same boolean)
- **Kenapa penting:** CoreERP built a six-level, organization-scoped security model for business apps and then governs itself with a boolean. Two concrete consequences. First, organization scope is not merely under-enforced (SEC-04) — it is architecturally incapable of constraining an administrator, so 'admin for Cabang Makassar' is unrepresentable and the org-scope UI's promise is void for exactly the people who most need bounding. Second, a tenant cannot delegate one administrative task without granting all of them: the person who should only invite staff also gains the ability to publish hierarchy versions and rewrite every role. docs/dev/09-identity-and-access.md's own table describes `admin` as 'Mengelola anggota, security role, assignment, dan konfigurasi tenant' as if that were one indivisible responsibility, which is the assumption to revisit before the model is load-bearing.
- **Perubahan yang diperlukan:** Decide and document the boundary explicitly: either (a) express Core administration as vendor-declared duties on a built-in `core` app registered through the same RegisterAppCatalog path (core.access.manage, core.organization.manage, core.number-sequence.manage, core.invitation.manage), so admin authority is composable and scopeable exactly like app authority and canManageAccess() becomes a permission lookup; or (b) keep the coarse system_role deliberately and document in docs/dev/09 that organization scope never applies to owner/admin, so no one builds a UI promising a scoped admin. Do not leave a scope model that silently does nothing for administrators. Owner: Core.

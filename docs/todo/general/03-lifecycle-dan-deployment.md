## Blocker

### [ ] `LIFE-01` — DeployAppPlacement cannot run in any environment this repo produces: no release root, no docker CLI, no docker socket

**Jenis:** missing-core-capability · **Verifikasi:** CONFIRMED · **Memblokir:** placement, installation, ready, web-shell, provider-console, procurement

- **Dynamics 365:** LCS deploys through a real deployment agent (Service Fabric / AOS deployment, LCS Deployable Package + Environment) that exists on the target and reports back. The orchestrator never assumes it can shell out to the host's container runtime.
- **Keadaan sekarang:** The worker shells out to `docker compose` from inside the Laravel process, in a directory derived from COREERP_RELEASE_ROOT + release.bundle_path. COREERP_RELEASE_ROOT is read by config but is not present in .env.example, so any env created from the example makes the job throw before doing anything. The control-plane image installs no docker CLI and mounts no docker socket, and the worker container runs `queue:work` inside that same image.
- **Bukti:** apps/core/config/coreerp.php:10 ('release_root' => env('COREERP_RELEASE_ROOT')); apps/core/app/Jobs/DeployAppPlacement.php:183-186 throws 'Release root has not been configured.'; :101-102 Process::path(...) + ['docker','compose',...]; apps/core/.env.example:32-36 lists COREERP_DEPLOYMENT_* but no COREERP_RELEASE_ROOT; apps/core/Dockerfile:16-21 installs only PHP extensions (no docker-ce-cli), :28-31 entrypoint roles web/scheduler/worker; apps/core/docker/entrypoint.sh:22 runs queue:work in that image
- **Kenapa penting:** The single most important lifecycle capability — turning entitled into installed and ready — is dead on arrival in both local docker development and the documented Dokploy topology. Every 'ready' placement that exists today therefore came from a hand-written SQL insert or a data migration, not from the worker.
- **Perubahan yang diperlukan:** Core: replace in-process shell-out with a deployment-target adapter (an interface with a Dokploy/API implementation and a local-compose implementation for dev), invoked over the network, so the control-plane container never needs a container runtime. Add COREERP_RELEASE_ROOT (or the adapter's target config) to .env.example and fail fast at boot, not at job time. Owner: Core.

### [ ] `LIFE-02` — There is no real health check; runtime_status='ready' only proves a container reached 'running'

**Jenis:** wrong-model · **Verifikasi:** CONFIRMED · **Memblokir:** ready, launcher, upgrade

- **Dynamics 365:** LCS/AOS readiness is an actual application-level probe plus a smoke check before an environment is marked deployed; the environment page reports service health, not container state.
- **Keadaan sekarang:** The worker's only readiness evidence is `docker compose up -d --wait --wait-timeout 300 <api> <ui>`. `--wait` falls back to 'running' for services with no healthcheck. The app template's compose declares a healthcheck ONLY on the database service, not on api or ui. The app's own /api/v1/health endpoint exists but returns a hardcoded literal and is never called by Core.
- **Bukti:** apps/core/app/Jobs/DeployAppPlacement.php:116-125 (up --wait then immediately writes runtime_status='ready', ready_at); D:/Kerja/app-erp-template/deploy/compose.yaml:10-14 healthcheck on app-db only, :16-31 app-api and app-ui have none; D:/Kerja/app-erp-management-aset/api/app/Http/Controllers/HealthController.php:9-12 returns ['status' => 'ready'] with no DB/migration check; D:/Kerja/app-erp-management-aset/api/routes/api.php:27 route exists; no HTTP call to any app health endpoint anywhere in apps/core/app
- **Kenapa penting:** docs/dev/10:36 requires 'menunggu health check nyata'. A crash-looping or unmigrated API that merely starts will be marked ready, the launcher will show it, and users get errors inside the iframe with no failure state to read. This is the clearest case of faking success in the dimension.
- **Perubahan yang diperlukan:** Core: after compose brings services up, poll the app's health URL over HTTP with a timeout and require a 200 plus a migration-state assertion before writing runtime_status='ready'; record the probe result on the app_installations row. Apps: HealthController must verify DB connectivity and that no migrations are pending, and compose fragments must declare healthchecks on api and ui. Owner: Core for the probe, app for the endpoint.

- **Kenapa penting:** This is a doc-code drift with the largest downstream blast radius in the whole design. docs/dev/14:111 makes the outbox load-bearing for continuous number sequences: the app is required to write its business transaction and a confirm/cancel outbox record in one transaction, and a worker must retry until Core answers. ### [ ] `LIFE-09` — Manifest security schema drift: the app skips the privilege layer and the entry-point indirection, and RegisterAppCatalog collapses all three levels into identical 1:1:1 rows

**Jenis:** wrong-model · **Verifikasi:** CONFIRMED · **Memblokir:** sod, field-level-permission, access-audit, procurement

- **Dynamics 365:** D365 F&O security is menu item / entry point -> permission (entry point + access level) -> privilege (a set of permissions) -> duty (a set of privileges) -> role. The privilege layer is what makes duties reusable and what SoD analysis operates on.

AppCatalogRequest validates the app's shape, not the docs' shape. RegisterAppCatalog then synthesizes, per permission code, one app_entry_points row, one permissions row, and one security_privileges row all sharing the identical code, with entry_point_code = the permission code and access_level = the substring after the last dot.
- **Bukti:** docs/dev/02-module-standard.md:63-81 (entryPoints/permissions with entryPoint+access/privileges/duties with privileges); D:/Kerja/app-erp-management-aset/app.yaml:49-146 (permissions with type only), :147-203 (duties -> permissions); D:/Kerja/app-erp-template/app.yaml:22 ('permissions: []' — a third, different shape); apps/core/app/Http/Requests/Provider/AppCatalogRequest.php:30-37 (permissions.*.type in [form,action]; duties.*.permissions); apps/core/app/Actions/Provider/RegisterAppCatalog.php:26-47 (entry point, permission, privilege all keyed on $permissionData['code']; access_level = str($code)->afterLast('.'); privilege->permissions()->sync([$code])); :49-56 duty->privileges()->sync($dutyData['permissions']); same collapse in database/seeders/AppCatalogSeeder.php:29-62; schema at database/migrations/2026_07_20_000000_create_core_identity_access_tables.php:128-160
- **Kenapa penting:** app_entry_points, permissions.entry_point_code, permissions.access_level, security_privileges and security_privilege_permissions all exist but carry no information beyond the permission code — three tables and two join tables encoding one flat list. If the flat shape is intentional, delete app_entry_points, permissions.entry_point_code, security_privileges and security_privilege_permissions and rewrite docs/dev/02 — but that forfeits SoD and entry-point permissions. If the D365 shape is intentional (recommended, given the stated baseline), extend AppCatalogRequest and RegisterAppCatalog to ingest entryPoints and privileges as distinct levels, update app.yaml in both app repos, and fix the template. Owner: Core for the schema and ingestion, app for the manifest.

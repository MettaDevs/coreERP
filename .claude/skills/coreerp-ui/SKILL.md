# CoreERP UI

Use `@apperp/ui@0.6.2` as the single source for generic UI. Inspect its components before adding markup or CSS. Add a shared component only when existing primitives cannot compose the required behavior. A thin wrapper over an existing primitive is acceptable when its purpose is to keep one non-obvious behavior identical across apps; say so in the file's doc comment. `@apperp/ui/collapsible-section` is such a wrapper over `Accordion`: what it standardizes is the value summary that stays readable on the header line while the section is closed. `@apperp/ui/transfer-list` is a dual-listbox picker (unassigned left, assigned right, single/bulk transfer buttons) for assigning a bounded reference list to a record — use it instead of a `MultiSelect` combobox when both sides need to stay visible at once.

## Pilih layout dari pekerjaan pengguna

- Entitas kompleks dengan banyak field, FastTab, rincian, atau relasi, seperti aset, memakai **DataTable + kartu popup SDK PageDialog**. Kompleksitas record bukan alasan otomatis memakai split view. Tambah, Detail, dan Ubah membuka kartu milik resource; daftar, filter, sort, dan scroll tetap terpelihara di belakangnya.
- Split view `MasterDetailLayout` dipakai bila pengguna perlu berpindah antar-record sambil menjaga konfigurasi/detail ringkas terlihat berdampingan. Jangan memaksakannya pada kartu entitas kompleks.
- Editor **Buku dan Metode Penyusutan** memakai `GroupBookMatrix`: kartu per buku dengan field berkelompok, masa manfaat tahun/bulan melalui `ServiceLifeFields`, serta nilai bawaan metode. Pertahankan editor ini untuk draft dan record tersimpan; jangan menggantinya dengan tabel generik lebar atau input periode mentah. Pada draft, perubahan diteruskan ke induk dan tidak menyediakan Simpan tersendiri.
- Form tambah/edit yang dibuka dari DataTable memakai `@apperp/ui/page-dialog`, dengan body yang bisa digulir dan `PageDialogToolbar` di atas body untuk Simpan/Batal. Dialog compact tetap untuk konfirmasi atau quick-create kecil. Sheet dipakai untuk panel bantu/konteks atau bila pengguna secara eksplisit meminta bentuk tersebut.

### Bar perintah ringkas

- Ikuti susunan BC yang ringkas melalui komponen SDK: `RecordActionBar` untuk perintah halaman, `CardHeader` + `CardAction` untuk perintah Card, dan `PageDialogToolbar`/`DialogToolbar` untuk aksi kartu form. Kepadatan tombol ditetapkan oleh bar tersebut, bukan override tinggi/font/border pada tiap halaman.
- Semua aksi Baru/Tambah halaman berada di kiri. Simpan tetap eksplisit, berada di kiri atas dan mendahului Batal; tidak ada auto-save baru. Bar perintah tetap terlihat saat body digulir dan membungkus pada ruang sempit. Menu widget tambahan boleh memakai `CardAction align="end"`; ini bukan tempat tombol Baru halaman.
- Gunakan `ActionButton` untuk perintah record: `create` berlabel **Baru** (+), `edit` **Ubah**, `save` **Simpan** (disk), `cancel` **Batal** (X), dan `archive`/`delete` **Delete** (tempat sampah). Label dan ikon ditetapkan SDK; jangan kirim children atau menulis ulang judul seperti “Tambah alamat”. `pending` menampilkan status menyimpan/memproses dan mencegah klik ulang. Perintah tampil inline tanpa border atau latar berisi; tombol autentikasi dan konfirmasi mengikuti konteksnya sendiri. Label Delete pada `archive` tidak mengubah handler, permission, `deleted_at`, atau cara data disimpan.
- Pilih berdasarkan makna: `create`/Baru membuka kartu record baru; `add`/Tambah menambah baris rincian atau memasukkan record ke kelompok atau dokumen, misalnya aset ke polis atau organisasi ke hierarki. Membuat dokumen, aturan, job, atau relasi bertanggal baru tetap Baru walaupun formnya memilih referensi. Jangan mengganti semua relasi menjadi Tambah tanpa membaca apa yang dibuat. Ukuran perintah ditetapkan SDK; pemanggil tidak mengirim `size` atau menggambar ikon/label sendiri.
- Form record yang dibuka dari DataTable tampil sebagai kartu `PageDialog` di atas daftar yang tetap terpasang, termasuk Party dan Vendor. Jangan mengganti seluruh daftar dengan form inline atau membuat split view untuk alur tersebut. Body/filter memberi jarak atas bagi floating label dan scroll padding agar label tidak tertutup bar perintah.
- Toolbar form ditempatkan sebelum body dalam DOM. Pertahankan form pemilik, `type="submit"`, atribut `form` yang sudah diperlukan, validasi, izin, pending state, dan portal dropdown. Jangan memakai CSS `order` atau portal untuk memindahkan aksi simpan. Footer konfirmasi, pemilih, dan panel bantu tidak otomatis menjadi toolbar entity.
- Intent `save` dan `add` wajib menyebut `type="submit"` untuk submit native atau `type="button"` untuk handler klik. Intent lain selalu tombol biasa; Batal tidak boleh menjadi submit. Type SDK menegakkan pilihan ini agar pemindahan toolbar tidak diam-diam mengubah perilaku form.
- Judul bar halaman dan nama fitur pada header kartu memakai 14 px semibold, teks operasional 14 px, header kolom tabel 12 px regular, dan FastTab 18 px semibold dengan padding rapat. Tombol perintah default setinggi 28 px; perangkat pointer kasar mendapat target 44 px. Perintah biasa berikon dan berlabel; aksi ikon pada header kartu memakai nama aksesibel serta keterangan hover/focus. Fokus keyboard tetap terlihat, dan preferensi keluarga font pengguna dipertahankan.

## Boundaries

### Daftar dan pilihan dimuat bertahap saat scroll

Keputusan pemilik produk: semua daftar record, DataTable, list, pemilih lengkap, dan dropdown record database memakai pemuatan bertahap saat scroll seperti Business Central. Jangan menyediakan tombol nomor halaman, sebelumnya/berikutnya, atau mengambil seluruh tabel lalu memotongnya di browser. Pembagian batch di server tetap diperlukan; larangan ini mengenai navigasi halaman pada UI.

- Gunakan `useIncrementalList` dari `@apperp/ui/use-incremental-list` dan prop `incremental` pada `DataTable`; pemakai module memakai adapter `useRecordList`. Halaman dengan props Inertia memakai `Inertia::scroll()` dan adapter `RecordListScroll`, dengan reset hasil saat filter berubah. Dropdown record memakai loader `InlineLookup`; `MasterSelect` adalah adapter master module. Jangan membuat fetch/scroll engine per halaman.
- Search, filter, dan sort berlaku di server terhadap seluruh hasil yang diizinkan, sebelum batas batch. Pertahankan tenant, perusahaan, organisasi, parent/dependency, dan permission pada setiap batch. Allowlist kolom sort/filter; jangan meneruskan nama kolom dari browser langsung ke SQL.
- Gunakan urutan stabil dengan pembeda ID, tangani nilai NULL dan angka dengan benar, batalkan request basi saat pencarian/filter/scope berubah, cegah fetch bersamaan dan duplikasi, hentikan pada akhir hasil, serta sediakan error/retry dan akses keyboard. Perubahan scope membatalkan hasil lama.
- `IncrementalList` di Core menyediakan batas batch dan cursor untuk query yang sudah diberi scope. Mapping kolom milik resource; jangan menganggap label UI sebagai nama kolom SQL. Jangan menghitung total seluruh hasil untuk sekadar membuka daftar.
- Enum pendek dan rincian draft yang memang sudah dimiliki form tetap lokal; ini bukan alasan mengambil semua record database untuk pilihan. Export, agregat laporan, dan pilih-semua lintas hasil harus punya operasi server sendiri, tidak bergantung pada batch yang telah dilihat.
- Uji pencarian record di luar batch pertama, pergantian filter/sort cepat, urutan dengan nilai sama/NULL, akhir daftar, kegagalan batch lanjutan, serta isolasi tenant/scope. Build saja belum cukup: ikuti verifikasi runtime UI di AGENTS.md.

Dasar: [Business Central: Making pages load faster](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/performance/performance-users#making-pages-load-faster). Lazy loading data berbeda dari virtualisasi baris; virtualisasi saja tidak mengurangi jumlah data yang diambil server.

- Web Shell owns the launcher, shared header, rail, sidebar, search, notifications, appearance, and account controls.
- An app owns only its business content and does not recreate Shell navigation.
- App CSS may define layout and domain presentation. It must not redefine fonts, tokens, controls, dialogs, tables, focus rings, invalid/disabled/loading states, or dark mode.
- Divider antar panel memakai garis polos tanpa grip, titik, tonjolan, atau tombol kecil di tengah. Untuk `ResizableHandle`, jangan pasang `withHandle` kecuali pengguna secara eksplisit meminta grip visual. Pertahankan area seret, cursor resize, fokus, dan akses keyboard meskipun grip tidak ditampilkan.
- Redefining an SDK component from the page has three recognisable shapes, and all three are the same mistake. Reaching into its internals with arbitrary variants (`[&_thead_th]:bg-primary` on `DataTable`); zeroing the spacing it owns (`CardHeader className="py-0"`); or re-implementing what it already does (`DialogContent` given `fixed top-1/2 left-1/2 -translate-*` when it centres itself, where a `size` prop is then silently overridden by a `max-w-*` on the same element). Each one makes that screen drift from every other screen, and each one breaks quietly when the SDK changes its internal markup — no error, just a style that stops applying. If the new look is right, it belongs in the SDK as a variant so every screen gets it; if it is right for one screen only, it is probably not right.
- Do not copy Control Plane source. Import public subpaths such as `@apperp/ui/input`, `@apperp/ui/dialog`, and `@apperp/ui/table`.
- A module renders inside the Core Shell. Do not add a second rounded, bordered page container when the Shell already provides the page frame.
- For a Shell sidebar, apply a custom `--sidebar-width` to the SDK Sidebar root so its spacer and rendered panel always share the same width. Rail width and hover-panel offset must use the same `--sidebar-width-icon` variable.
- Label menu sidebar, baik rail maupun submenu, tampil penuh tanpa elipsis (`...`), `truncate`, atau line clamp. Biarkan teks membungkus dan tinggi item bertambah; daftar boleh digulir vertikal. Status aktif memakai warna/latar/indikator, tanpa mengubah ukuran atau ketebalan huruf, agar pemilihan menu tidak menggeser atau mematahkan teks. Jangan mengganti label penuh dengan tooltip.
- Use `DataTable` from `@apperp/ui/data-table` for dense operational lists; do not rebuild these tables with `Table` or plain HTML. Show bulk actions only after rows are selected. Keep a list header compact; do not spend a tall card section on a title that has no additional context. Headers wrap to multiple lines; only a single header word wider than the available width receives an ellipsis. Row values stay on one line by default and use an ellipsis when they exceed the column width. Both headers and row values show their full text on hover by default. For custom cell markup, use `DataTableText` around its text; use `multiline` only for headers or an explicitly requested multiline value. Resizing moves a full-height drag guide while the pointer is held; column widths change only on release, and cancelling leaves widths unchanged. Text must never overlap its neighboring column. A record master rendered as the two-pane layout below is the exception: its left pane replaces the table.
- **Row actions must use the SDK's `⋯` menu through `actions` and `onRowAction`, with `actionsPlacement="inline"`.** Put the code/primary identity in the first data column so the menu appears immediately after it. For records with a code and name, use separate columns in this order: **`# → code → ⋯ → name → other fields`**. Selection checkboxes, when needed, remain in the SDK's leading selection column. Do not place actions at the far right or replace the menu with per-row buttons such as “Atur”, “Ubah”, or “Lihat”; those actions belong inside the menu. Use `actionsPlacement="trailing"` only when the user explicitly requests that placement.

### Pilihan baris pada tabel master-detail

Import frame `Table` dari `@apperp/ui/table` maupun elemen HTML `<table>` pada UI module ditolak ESLint. Gunakan kolom `DataTable`; baris komposit yang memerlukan hook sendiri memakai `renderRows` di dalam frame DataTable yang sama.

Pada `DataTable`, membuka detail baris memakai event native `onDoubleClick` secara default, bukan klik sekali atau penghitung klik dengan timer. `onRowClick` adalah callback aktivasinya; `rowActivation="single-click"` hanya untuk memilih baris aktif tanpa membuka detail. Menu `⋯`, checkbox, link, dan kontrol edit tidak boleh ikut memicu pembukaan baris. Enter/Space saat fokus berada pada baris menyediakan aktivasi lewat keyboard; kontrol di dalam baris mempertahankan perilaku keyboard-nya sendiri.

Sebut pola ini **tabel master-detail dengan pilihan baris**. Pilih bentuknya dari kebutuhan kerja, bukan dari tampilan:

- Jika pengguna hanya perlu membuka satu detail dan tidak ada tindakan massal, gunakan **pilihan tunggal**: satu `selectedRowId`, klik baris atau keyboard memindahkan detail ke panel di bawah tabel.
- Jika beberapa baris harus tetap ditandai untuk tindakan massal, gunakan **multi-select dengan checkbox** dan state terpisah untuk `checkedRowIds` serta `activeRowId`. Jadikan checkbox sebagai kolom pertama yang berdiri sendiri agar pengguna dapat menandai banyak baris dengan cepat. Seluruh sel pada kolom checkbox—bukan hanya kotak kecilnya—menjalankan aksi yang sama; sel header demikian pula untuk pilih/batal pilih semua dan menunjukkan keadaan sebagian-terpilih. Checkbox baris menambah atau menghapus tanda tanpa menghapus checkbox lain; semua yang ditandai bertone lebih terang dan yang terakhir dicentang menjadi aktif dengan tone lebih gelap serta detail di bawah. Hentikan propagasi klik checkbox agar satu klik tidak diproses lagi oleh sel atau baris induknya. Jangan menyamakan “dicentang” dengan “detail yang sedang dibuka”.
- Saat tabel pertama kali dimuat, default-nya **tidak ada baris dipilih atau dicentang**, sehingga panel detail tidak tampil. Buka baris awal hanya bila kebutuhan layar secara eksplisit menyatakannya.
- Klik area baris, sel, atau kontrol edit di dalam tabel dengan pointer adalah **pilihan tunggal**: hapus tanda checkbox sebelumnya, tandai hanya baris yang diklik, lalu tampilkan detailnya. Checkbox menghentikan propagasi klik agar mempertahankan mode multi-select miliknya sendiri. Ketika checkbox aktif dibatalkan, pindahkan detail ke checkbox terakhir yang masih ditandai atau sembunyikan detail bila tidak ada lagi.
- Handler keyboard pada baris hanya boleh memproses `Enter`/`Space` ketika target fokusnya adalah baris itu sendiri. Jangan memanggil `preventDefault()` untuk event yang berasal dari `Input`, `Textarea`, `Select`, `Checkbox`, atau kontrol edit lain di dalam baris maupun panel detail; spasi dan tombol lain harus tetap bisa diketik normal. Panel detail mengikuti keyboard native masing-masing kontrol dan tidak boleh diperlakukan sebagai bagian dari shortcut baris.
- Keyboard row-selection harus setara dengan klik hanya saat fokus berada di baris: `Enter`/`Space` pada baris memilihnya, sedangkan pada kontrol edit tetap menjalankan fungsi kontrol tersebut.
- Gunakan `Table` dan `Checkbox` dari SDK; jangan membuat checkbox, tabel, atau warna seleksi buatan sendiri. Buat komponen bersama hanya setelah sedikitnya dua layar memakai bentuk interaksi, state, dan penempatan detail yang sama. Sebelum itu, komposisikan primitif SDK secara lokal agar tidak memaksakan pola ke tabel biasa.

Saat memberi tugas ke AI, nyatakan kebutuhan ini secara langsung, misalnya: “Buat tabel master-detail dengan kolom checkbox khusus dan checkbox pilih-semua pada header. Checkbox mendukung pilihan banyak; klik baris atau field menjadi pilihan tunggal. Baris yang sudah dicentang tetap bertone ringan, baris aktif terakhir bertone lebih gelap, dan detailnya muncul di bawah tabel.”

- Select biasa mengikuti lebar trigger. Untuk lookup record bertabel, field boleh ringkas sedangkan popup lebih lebar agar kolom terbaca. Tentukan lebar dari isi/kolom, tetap sejajar dengan field, batasi ke ruang viewport/overlay yang tersedia, dan sediakan scroll horizontal bila kolom tidak muat; jangan memperlebar field hanya untuk menampung tabel.
- For `Select` or combobox controls inside an SDK `Sheet`, `Dialog`, Popover, or another overlay, pass that overlay's content ref as `portalContainer`. Without it, the menu can render beneath the overlay and look open while its options cannot be clicked. This is a mandatory implementation rule; see the repository-wide rule in [`AGENTS.md`](../../../AGENTS.md#ui-overlay-dropdowns).

## Lookup action decision gate

Saat menambah atau mengubah lookup, putuskan bentuk field dan kemampuan tiap aksinya sebelum memasang tombol. Gate tiap aksi tetap **independen**. Untuk `InlineLookup`, Detail dan Daftar lengkap tersedia secara default melalui dialog bawaan berbasis data yang sudah diizinkan. Sembunyikan lewat `showDetails={false}` / `showFullList={false}` bila gate resource/hak melarang. Jangan menyalin izin dari tombol lain atau menampilkan tombol tanpa aksi yang berfungsi.

| Keputusan | Kapan dipakai | Syarat aksi muncul |
| --- | --- | --- |
| Select biasa | Enum/pilihan tetap yang pendek, tanpa record master untuk dibuka atau dibuat. | Tidak memiliki New, Detail, atau Daftar lengkap hanya untuk menyerupai BC. |
| Inline lookup | Referensi ke record; pengguna mencari kode/nama/deskripsi langsung di field. | Label tetap terbaca; pilihan menampilkan identitas yang cukup. Query sementara terpisah dari nilai yang sudah dipilih. Popup tidak menambahkan input pencarian kedua atau paragraf petunjuk keyboard. |
| **Daftar lengkap** | Pencarian ringkas tidak cukup: perlu membandingkan kolom tambahan, filter, atau paging. | Pemilih/list provider benar-benar ada dan izin membaca/memilih dipenuhi. Tetap menerapkan tenant, organisasi, parent/dependency, dan batas data yang sama dengan lookup ringkas; “lengkap” berarti seluruh data **yang boleh dipilih**, bukan seluruh database. |
| **Detail** | Record memiliki informasi relevan di luar kolom lookup dan tujuan detail yang jelas. | Resource mendukung detail dan pengguna boleh membaca record sasaran. Sasaran adalah baris yang sedang disorot dalam hasil yang sah, lalu nilai committed bila sesuai konteks; jangan menebak record pertama. Jika dukungan/izin tidak ada, sembunyikan. Jika dukungan ada tetapi belum ada sasaran, boleh tampil nonaktif. Hak melihat detail tidak memberi hak mengubah. |
| **Baru** | Pengguna memang boleh membuat master tersebut sambil mengisi field; record baru bisa segera dipakai. | Ada alur create milik resource, izin create, dan scope/dependensi sudah diketahui. Sembunyikan untuk enum, data sistem/eksternal yang dikelola pihak lain, atau resource yang harus lahir lewat workflow/onboarding/approval lain. Backend tetap memeriksa izin dan scope saat menyimpan. |

**Kontrak perilaku yang ditentukan pengembang:**

- `InlineLookup` tidak menyediakan tombol X atau unselect, dan tidak memanggil `onValueChange(null)`. Menghapus teks hanya mengubah query sementara; menutup field/popup memulihkan label record yang sudah dipilih. Nilai awal boleh kosong, tetapi record yang sudah dipilih hanya diganti dengan pilihan record lain secara eksplisit. Jangan menambahkan opsi `clearable` untuk menghidupkan lagi perilaku yang dilarang ini.

- Putuskan **label tampilan setelah dipilih** terpisah dari ID/kode yang disimpan. Utamakan nama/deskripsi yang paling mudah dikenali manusia; kode dipakai bila memang identitas kerja yang dikenal pengguna (misalnya nomor akun), bukan sebagai default universal. Bila nama ambigu, pilih kombinasi nama + pembeda yang relevan. Jika agent tidak tahu atau konteks rancu, **tanyakan developer apa yang harus tampil saat record dipilih**, jangan menebak dari nama kolom. Jangan menambah deskripsi record di bawah field untuk menutupi label pilihan yang kurang tepat; tampilkan pembeda di field/popup.
- Header lookup bertabel memakai DataTable SDK beserta sorting dan resize kolomnya, bukan grid header buatan sendiri. Header dan baris harus berbagi ukuran kolom serta scroll horizontal. Resize lewat pointer menampilkan guide dan diterapkan saat dilepas; keyboard tetap tersedia sesuai DataTable. Pemilihan dengan panah/Enter dan label combobox tetap bekerja saat tabel dipakai dalam popup.
- Detail harus tetap dapat dibuka untuk nilai yang sudah dipilih, tanpa harus menyorot ulang baris. Sorotan sah boleh menjadi target saat pengguna menelusuri hasil; query tanpa hasil tidak boleh membuka record lain secara diam-diam. Perubahan nama pada kartu memperbarui label field dan pemilih yang mereferensikan record itu.
- Detail boleh menyediakan **Ubah/Simpan/Batal** jika resource mendukung edit dan pengguna punya izin edit record tersebut. Izin baca/detail dan create tidak menyiratkan izin edit. Default read-only, masuk edit secara eksplisit; Batal mengembalikan draft, Simpan memperbarui record tanpa mengubah identitas/referensi pilihan. Inline Edit List merupakan keputusan terpisah; jangan otomatis mengaktifkannya hanya karena kartu boleh diedit.

- Deklarasikan kemampuan resource dan hasil otorisasi terpisah (`canRead`, `canCreate`, tujuan list/detail/create). Checkbox simulasi hanya boleh ada di playground; bukan mekanisme otorisasi produk. Field read-only tidak menawarkan aksi yang mengubah referensinya.
- Daftar lengkap membuka pemilih dengan pilihan sementara. Klik baris memindahkan kandidat; tombol **Pilih/OK** mengisi field. **Batal/Escape/tutup** mempertahankan nilai sebelumnya. Memeriksa Detail lalu kembali tidak melakukan commit. Pencarian di toolbar pemilih lengkap boleh ada; itu berbeda dari input pencarian kedua dalam dropdown ringkas.
- Detail membuka target yang tepat tanpa mengubah referensi. Gunakan halaman master/detail milik resource yang sudah ada; jangan membuat salinan master di module pemanggil. Form edit hanya boleh tersedia melalui gate edit tersendiri. Simpan query, kandidat, dan scroll pemilih saat kembali.
- Untuk Baru, tentukan secara eksplisit: quick-create form, kartu master, atau baris edit di daftar. Pilih dari kebutuhan dan validasi resource, **bukan** satu mekanisme global untuk semua lookup. `Edit List` adalah kemampuan edit tersendiri; jangan menyimpulkannya dari izin create.
- Putuskan penomoran manual/otomatis sesuai [number-sequence-design](../number-sequence-design/SKILL.md), field wajib, validasi unik, default aktif, dan penanganan kegagalan. Gagal menyimpan mempertahankan input serta menampilkan error yang tetap terlihat.
- Setelah create sukses dari lookup, gunakan respons record lengkap (ID, kode, nama/deskripsi, status yang relevan) untuk memperbarui daftar dan memilih record itu tanpa pencarian ulang. Jika bisnis mengharuskan pengguna tetap berada di kartu baru, nyatakan keputusan tersebut. Membatalkan draft tidak membuat record. Membatalkan pemilih tidak membatalkan record yang **sudah disimpan** oleh aksi create/edit.
- Untuk `InlineLookup` dalam Dialog Radix, pasang guard `DialogContent.onEscapeKeyDown`: bila content ref masih memuat `[role="combobox"][aria-expanded="true"]`, panggil `event.preventDefault()` agar dialog induk tetap terbuka sementara popup menangani Escape. Lihat contoh pada playground dan dialog alamat organisasi.
- Hormati portal overlay, fokus kembali ke pemanggil, dan Escape per lapisan: popup lebih dulu, lalu dialog teratas. Uji semua kombinasi kemampuan yang tersedia/tidak tersedia, tanpa pilihan, hasil kosong, batal, detail, create gagal, serta create berhasil. Jangan otomatis mengaktifkan seluruh aksi pada Select global karena contoh playground memilikinya.

**Dasar BC dan batas penerapannya:** [Entering data](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-enter-data#finding-data-as-you-type) membedakan enum dropdown dan lookup record. [LookupPageId](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/properties/devenv-lookuppageid-property) menentukan tujuan lookup dan menyarankan lookup ringan agar tidak menjalankan seluruh trigger/FactBox halaman master. [CardPageId](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/properties/devenv-cardpageid-property) menentukan kartu tujuan. Pada BC yang diamati 15 Oktober 2026, Show details pada FA Posting Group membuka kartu record; pemilih lengkap memakai OK/Cancel; New pada daftar yang mendukung Edit List dapat menambah baris kosong. Itu contoh variasi konfigurasi resource, bukan kewajiban meniru inline editing atau mengizinkan CRUD di setiap pemilih. Komponen bersama pola ini adalah `InlineLookup` dari `@apperp/ui/inline-lookup`; playground `apps/core/resources/js/pages/inline-lookup-demo.tsx` memakai komponen yang sama, bukan implementasi paralel. Gunakan `columns` DataTable dan pisahkan `getItemValue` (identitas), `getItemLabel` (teks pilihan), serta `getSearchText` (pencarian). Detail dan Daftar lengkap tampil secara default dan memakai dialog SDK berdasarkan `items`/`columns` yang telah diizinkan. `onDetails`/`onFullList` boleh menggantinya dengan halaman bisnis khusus; `showDetails={false}`/`showFullList={false}` menyembunyikannya melalui gate eksplisit. Baru tetap memerlukan callback `onCreate` beserta izin create. Detail bawaan hanya baca, tidak memberi izin edit, dan tidak menampilkan field di luar kolom yang diberikan. Record server wajib memakai `loadItems({query, cursor, signal})` yang mengembalikan batch dan `nextCursor`; jangan fetch seluruh master lalu memotong tampilannya. Popup dan Daftar lengkap berbagi hasil/cursor, memuat batch berikutnya saat scroll, dan mempertahankan header. Pembukaan awal tanpa debounce, pencarian ketikan memakai debounce 250 ms. Cache field 30 detik dibatalkan pada perubahan source/scope dan aksi tulis; bukan cache global lintas tenant. Tidak ada navigasi nomor halaman; props pagination/page/onPageChange ditolak. Array `items` hanya untuk data lokal yang memang sudah dimiliki halaman. Komponen menjaga query sementara, target Detail, sorting, resize, dan portal; pemanggil memiliki data, otorisasi, dan alur dialog bisnis. Select biasa tetap dipakai untuk enum.

## Page/card stack decision gate

- Kartu/form/pemilih yang memang diluncurkan sebagai modal halaman memakai `@apperp/ui/page-dialog`: `PageDialog`, `PageDialogContent` dengan `title` wajib dan `description` opsional, `PageDialogBody`, serta Footer/Action bila diperlukan. Jangan menyalin frame/registri/CSS dari R&D; demo dan pemakai kartu/modal harus memakai SDK yang sama.
- Penerapan mencakup kartu entitas dari DataTable, modal Address Book, dan lookup terkait. `PageDialogContent` memiliki susunan tetap: bar atas berisi Back dan nama fitur, lalu ikon Ubah, Bagikan, Baru (+), Delete; di kanan ada buka di tab baru, expand, dan Close. Di bawahnya tampil identitas record besar berupa kode/nomor dan nama, lalu navigasi utama, navigasi sekunder, dan isi kartu. `title` menamai fitur; `recordTitle` menamai record. Jangan menggabungkan keduanya atau membuat bar Back/judul kedua di isi kartu. `Dialog` compact, `AlertDialog` arsip/konfirmasi, popover kecil, tooltip, dan FieldHint tidak berubah menjadi page stack.
- Komponen anak dapat memakai `usePageDialogRecord` untuk mendaftarkan identitas, Ubah/Delete, status edit, URL record, serta navigasi yang benar-benar dimilikinya. Hook mengembalikan penanda apakah komponen berada dalam kartu SDK; sembunyikan tombol Back/Ubah/Delete versi isi ketika sudah ditangani header. Kirim `undefined` saat anak lain mengambil alih registrasi, misalnya kartu baca menampilkan form edit. Izin, konfirmasi, handler Delete, dan aturan dirty tetap milik halaman. Bagikan dan buka di tab baru memakai URL record yang benar-benar didukung router; jangan membuat tautan ke route atau query yang belum diimplementasikan. Navigasi utama/sekunder berasal dari layar yang nyata, bukan menu hias.
- SDK menyediakan kelompok Beranda untuk kartu record yang belum memiliki menu utama sendiri; aktivasi Beranda kembali ke awal isi kartu. Gunakan `PageDialogBody` atau tandai pemilik scroll kustom dengan `data-page-dialog-body`. Simpan/Batal tetap di toolbar form sebagai aksi kelompok tersebut dengan kepemilikan form asli. Deskripsi header opsional tersedia melalui ikon bantuan; jangan menyisipkan paragraf yang memisahkan identitas record dari navigasi.
- Kartu record memberikan `onNew` sesuai izin create dan `navigation` untuk record sebelumnya/berikutnya saat membaca atau mengedit record tersimpan. Gunakan `useRecordNavigation` dengan urutan daftar/filter/sort yang sama; jangan menebak ID atau memuat seluruh tabel. `busy` mengunci Back/Close/Escape dan navigasi selama penyimpanan. Guard draft juga berlaku pada tombol + dan navigasi, bukan hanya Batal.
- Detail milik record baru, seperti alamat, kontak, dan baris rincian, dapat diisi sebelum record pertama disimpan. Simpan draft secara lokal lalu kirim bersama induknya dalam satu transaksi. Batal tidak membuat record; kegagalan detail tidak meninggalkan induk setengah tersimpan. Jangan menambahkan instruksi “simpan dahulu” atau melakukan penyimpanan tersembunyi untuk mendapatkan ID.
- Pisahkan data tersimpan yang dimuat dari server dengan rincian draft milik kartu. Gunakan kunci lokal untuk baris draft; ID database baru diperoleh saat Simpan berhasil. Respons pemuatan, refresh daftar, dan perpindahan tab tidak boleh menimpa isian draft. Kegagalan pemuatan bukan daftar kosong. Ikuti [alur draft dan keadaan bagian kosong](../coreerp-page-standard/SKILL.md#draft-dan-bagian-kosong).
- Penyimpanan agregat mengirim identitas dan rincian miliknya dalam satu permintaan, memvalidasi seluruhnya, lalu menulis dalam satu transaksi. Pertahankan izin, batas tenant, aturan pemilik data bersama, versi, dan idempotency yang berlaku. Kesalahan rincian dikembalikan ke baris/field asal; draft tetap ada untuk diperbaiki. Jangan mengirim rincian lewat rangkaian request setelah induk telanjur tersimpan.
- Bedakan rincian draft milik induk dari record mandiri yang dibuat melalui lookup. Memilih record yang sudah ada tidak membuat salinan atau memberi izin mengubahnya. Saat menambahkan rincian baru ke Party yang sudah ada selama pembuatan Vendor, tampilkan data lama sebagai bacaan dan tahan tambahan sebagai draft sampai Simpan Vendor. Record mandiri yang sudah disimpan lewat kartu lookup memiliki siklus simpan sendiri; Batal pada pemilih tidak membatalkan penyimpanan tersebut.
- `PageDialogContent` otomatis memakai outlet `[data-shell-overlay-host]`, atau viewport bila tidak berada di Shell. Tidak memakai prop `size`. Header mengikuti hierarki fitur dan identitas record di atas; jumlah halaman hanya ditunjukkan ketika stack berlapis. `expanded`/`defaultExpanded`/`onExpandedChange` mengatur ukuran. Ref content tetap diberikan ke `portalContainer` Select/lookup.
- Fade adalah milik mesin overlay, bukan field. Isi `PageDialog` beserta portal pada content ref berada dalam satu stacking context (`core-page-dialog-contents`, z0); scrim inactive adalah sibling di atasnya (z1). Shell page-content juga terisolasi di bawah outlet overlay. Jangan menaikkan z-index scrim secara acak atau menambal warna/z-index label Input/Select/Textarea per halaman. Uji label kosong/fokus/terisi dan header tabel agar seluruh parent ikut fade, lalu kembali normal saat child ditutup.
- Pertahankan parent mounted saat membuka child; jangan menutup/unmount parent hanya untuk menampilkan kartu turunannya. SDK membuat lapisan bawah inert dan meredup serta mengembalikan fokus; state draft, pilihan, scroll, dan expand tetap milik halaman. Back/Close/Escape tidak melakukan save atau rollback record yang sudah tersimpan: caller menentukan commit/cancel draft melalui onOpenChange/aksi bisnis.
- Shell search/navbar tetap hidup; area halaman utama yang ditutup dibuat inert. Outside click tidak membuang draft. Escape diproses lapisan teratas dan popup field lebih dulu. Konfirmasi kecil di atas kartu tetap menggunakan AlertDialog/compact Dialog. Hormati reduced motion; jangan menambah blur/animasi layout.
- Uji stack minimal tiga lapisan, count pada layar sempit, Back/Close/Escape, fokus pemanggil, nilai draft dan scroll setelah kembali, popup portal, Shell search, dan penutupan semua lapisan yang memulihkan inert halaman utama.

## Build a screen

1. Import `@apperp/ui/styles.css` after Tailwind and add `@source '../node_modules/@apperp/ui/dist'`.
2. Compose `Field`, `FieldLabel`, `FieldDescription`, and `FieldError`. Every field may carry optional contextual help, but only complex or non-obvious fields need it. Keep field-specific help with the field, behind `@apperp/ui/field`'s `FieldHint`.
   - `FieldHint`'s `children` is a small dedicated icon placed beside the control, not the control itself. Wrapping the control was tried and reverted: it fires the tooltip every time the pointer merely passes over the field on its way to actually clicking it, which reads as noisy rather than helpful. A separate icon never overlaps the area the user interacts with.
   - Tempatkan ikon hint tepat setelah label atau tepi kontrol yang terlihat, dengan gap kecil (`gap-1`/`gap-2`). Jika kontrol membatasi lebar internalnya, jangan menaruh hint setelah wrapper `w-full`/`flex-1` atau memakai `justify-between`: ikon akan terpisah jauh dari field. Gunakan slot hint milik komponen; `InlineLookup` menyediakan prop `hint`. Periksa jarak terhadap kontrol sebenarnya pada layar lebar dan sempit, bukan terhadap batas wrapper.
   - Pada form, `InlineLookup` memakai label di dalam field seperti Input/Select/Textarea dan mengisi lebar kolom form yang diberikan pemanggil. Jangan memasang label kiri atau batas `max-w-*` internal yang menyisakan area kosong besar pada kolom. Jika suatu layar memang perlu field ringkas, pemanggil yang menentukan lebar kolomnya; komponen tetap mengisi ruang itu. Lebar popup tabel boleh berbeda dari lebar field.
   - Hover opens the hint after roughly one second and closes when the pointer leaves; clicking the icon toggles a persistent open state, and clicking it again closes it. Because the trigger is a real button, the same toggle is reachable by keyboard for free (Tab to it, then Enter/Space) — no separate wiring needed.
   - `FieldLegend`'s `hint` prop uses the same `FieldHint` underneath for a section title rather than a field control.
   - Use visible `FieldDescription` when the user needs the guidance before continuing, and always for load or validation failures — a failed reference lookup is a real problem, not a hint, and must never be hidden behind hover.
   - Keep required and error text visible. For record forms, render the generated code first, then the name, then classifications and dependent selections in their business sequence. A required dependency does not belong above the record identity just because it is required.
   - For every new master, reference, or configuration record that has an `aktif`/active flag, initialize it to active (`true`) in the create form and keep the server-side create fallback active as well. A newly saved record must be immediately available in active lookups; the user must not save it and then perform a second status action just to make it usable. Editing an existing inactive record must preserve its current state unless the user explicitly changes it.
   - A transaction document that uses a lifecycle such as `draft`, `submitted`, `scheduled`, or `completed` is not an `aktif` flag. Create it in the module's valid initial lifecycle state and do not force it to an artificial “active” state; the no-second-click rule applies to the record's usable initial state, not to skipping workflow controls.
   - Use an on-field label when the control supports it: `Input`, `Select`, and `Textarea` accept `label="…"` and render the label inside the field. Do not duplicate it with `FieldLabel`. Use `FieldLabel` only for controls without an on-field-label API, such as `Switch` and `Checkbox`.
   - Every required field must visibly show exactly one red `*` beside its clean label and be enforced by validation. For SDK on-field-label controls (`Input`, `Select`/combobox, and `Textarea`), pass `required={true}`; the primitive renders the single red indicator. Never put `*` into the label text. Omit `required` and the indicator for optional fields. If a primitive has no built-in indicator, add one explicit accessible indicator at the label layer—never combine both approaches.
3. Prefer `Input`, `Textarea`, `NativeSelect`, `Switch`, and `Button`.
   - For the row of actions that sits above a record screen — edit, add, status, archive, and the save/cancel pair while editing — use `@apperp/ui/record-action-bar` rather than laying out that row per screen. It keeps the bar visible while a long form is scrolled and wraps its buttons instead of clipping them on a narrow screen; the buttons themselves stay ordinary `Button` and `ActionButton` supplied by the caller.
   - Perintah record berulang memakai `@apperp/ui/action-button`, termasuk Simpan dan Batal. Semua perintah ini inline tanpa border; aksi bisnis lain memakai `Button variant="ghost"`. Konfirmasi tindakan tetap milik resource dan tidak dihapus karena tombol utamanya menjadi ringkas.
   - Never let colour be the only signal. Every action carries an icon and a text label as well, and colours come from the `success` / `warning` / `destructive` tokens so both themes stay correct. Do not write raw palette classes such as `text-yellow-500`: bright yellow measures 1.39:1 against the light background token and is unreadable, while the `warning` token measures 5.26:1.
   - `ActionButton` memasok label dan ikon kanonik; pemanggil hanya memberi `action`, handler, izin, state, dan prop form yang dibutuhkan. Label Delete dan ikon tempat sampah juga dipakai untuk endpoint arsip/penghapusan lunak, tanpa mengubah makna penyimpanannya.
   - **Never render a control whose endpoint does not exist.** Confirm the route and its verb in the router before wiring an action to it — a button posting to a path nobody implemented is not a placeholder, it is a promise to the user that fails at the click. The same check catches a path that exists under a different name: `settings/access/memberships/{membership}` is not `settings/access/members/{id}`, and only one of them is real.
   - A destructive action must respect the same permission the server enforces. When the payload carries a per-record flag such as `can_edit_access`, gate every action that record owns on it, not only the edit. Gating on `canManage` alone offers "delete" on rows the server will refuse — most visibly the tenant owner's.
4. Untuk form tambah/edit dari DataTable, gunakan kartu popup SDK `PageDialog` sesuai gate layout di atas. Gunakan body yang bisa digulir, toolbar Simpan/Batal di kiri atas, dan content ref sebagai `portalContainer` untuk Select/lookup. Jangan menggantinya dengan side Sheet hanya karena field banyak.
   - Untuk **record master** dengan daftar kiri dan detail kanan, gunakan `MasterDetailLayout` dari `@apperp/ui/master-detail-layout`: berikan `list`, `children` untuk detail, serta state `detailOpen` dan `onDetailOpenChange`. Setelah memilih/membuat record atau meminta Ubah, halaman membuka detail; SDK memiliki divider polos yang bisa diseret, batas lebar, breakpoint layar kecil, dan tombol Daftar. Panel tetap mounted ketika berganti daftar/detail agar draft dan scroll bertahan. Jangan menyalin mesin resize, breakpoint, atau tombol kembali per halaman. Navigasi kategori, editor workflow, tabel dengan rincian di bawah, dan drill-down banyak kolom bukan pola ini. Detail tetap memiliki scroll dan baris aksi sendiri; izin, pemilihan, konfirmasi draft, dan penyimpanan milik halaman. `portalContainer` tidak diperlukan pada detail halaman, tetapi tetap wajib untuk Select di overlay.
   - A record master may open read-only and switch to editing on an explicit action. When it does, never express read-only with `disabled`: a disabled control emits no click and takes no focus, so the user cannot click a value to start editing it. Use `readOnly` on text controls, and intercept the pointer on controls that have no read-only state. Use `AlertDialog` with `AlertDialogDescription` for confirmations. Use `DialogDescription` for context that must be visible in the dialog; do not hide required decision text behind a hover/click hint. Page/card descriptions remain optional and never replace field-level help.
   - Untuk perilaku klik-ke-edit, bungkus form dengan `RecordEditBoundary` dari `@apperp/ui/record-edit-boundary`, isi `editing`, `canEdit`, `onEdit`, dan `disabled` saat menyimpan. Klik label/field `Input` atau `Textarea` baca saja, atau aktivasi judul `CollapsibleSection`, meminta mode edit tanpa menyimpan. Enter/Space pada field baca saja juga meminta edit; keyboard fasttab tetap mengikuti SDK. Pemanggil tetap memiliki state, validasi, izin, Simpan, dan Batal. Pakai `editActivation={false}` untuk field yang selalu baca saja seperti hasil perhitungan. Field di portal luar boundary tidak mengaktifkan edit induknya.
   - Kontrol yang tidak punya `readOnly` dapat dibungkus `RecordEditControl` dari subpath yang sama, termasuk labelnya. Klik pertama mengaktifkan edit tanpa membuka/membalik nilainya; label dan kontrol asli mendapat fokus setelah edit. Pembatasan bisnis dan izin yang membuat kontrol tetap disabled tetap milik form. Data acuan baca saja dan versi yang sudah dipublikasikan tidak menjadi editable hanya karena memakai layout bersama.
5. Use SDK `DataTable`, `Card`, `Badge`, and `Empty`, dengan pemuatan bertahap saat scroll sesuai aturan daftar di atas. Jangan menambahkan navigasi halaman.
6. Keep end-user copy in everyday Indonesian and explain the action or impact.

## New pages inside Control Plane (Shell)

Two mistakes shipped a page with a doubled header and no way to reach it. Both are invisible in type-check and lint, so check them by hand.

- **Never wrap a Core page in `AppLayout`.** `resources/js/app.tsx` already assigns `AppLayout` as the default Inertia layout for every page outside `auth/` and `welcome`. A page that renders `<AppLayout>` itself gets the header, rail, and sidebar twice — the screenshot looks like a Shell inside a Shell. Return a fragment with `<Head>` and your `<main>`, and pass breadcrumbs through the page property instead:

  ```tsx
  export default function ReportExports(props: Props) { /* ... */ }
  ReportExports.layout = {
      breadcrumbs: [{ title: 'Ekspor laporan', href: '/reports/exports' }] satisfies BreadcrumbItem[],
  };
  ```

  Follow `pages/workflow-inbox.tsx` or `pages/settings/number-sequences.tsx`; do not follow older pages that still import `AppLayout` directly.
- **Every new route needs an entry in `components/app-sidebar.tsx`.** That file is the main Shell navigation the user sees (Dashboard, Organization, Data referensi, Nomor dokumen, ...). `layouts/settings/layout.tsx` is only the sub-navigation of the Profile/Security/Appearance pages; a link placed there alone is unreachable from the rail. Put the item under the existing group it belongs to and give it the Core screen permission that guards its route (`permission: 'core.<group>.read'`; the sidebar hides it from members who lack it, while the route enforces it), and add it to the settings sub-nav too only if the page uses that layout.
- **Verify by walking the rail**, not by opening the URL directly: open the Shell, click through the rail to the new page, and confirm one header and one sidebar. A page reached by typing its URL proves nothing about either rule.

## Theme and workspace build

Modules share the Shell's React tree, theme, and fonts; they do not create an iframe, a second React root, or a `coreerp.ready`/`coreerp.context` handshake. Import public `@apperp/ui` subpaths and inherit the Shell stylesheet.

`packages/ui` is an npm workspace in this repository. Core and Control Plane use `"@apperp/ui": "*"`; the root lockfile resolves the workspace. Run the existing `ui:build` script before consumer type-check/build. Local runtime builds use `erp-dev/start.ps1 -Build`, which builds the SDK and consumers inside Docker. Do not introduce a vendored tarball or import package source from another repository.

## Native page and table scrolling

- Operational lists use `ListPageLayout` from `@apperp/ui/list-page-layout` as their page root, with `header`, `filters`, `footer`, and the primary table as children. It marks `data-layout="full-height"` and centralizes the flex/height rules; do not reproduce those wrappers on every page.
- The Shell fixes the viewport height, keeps its header/banners outside the scrolling content, and gives full-height pages the remaining space. Do not set `html`/`body` overflow or style every `main` from module CSS. Module wrappers above a full-height layout must propagate `h-full min-h-0` rather than grow with the records.
- A DataTable inside ListPageLayout automatically uses `viewport` scroll mode: one native container owns both axes, its horizontal scrollbar stays at the visible bottom, and its column header is sticky. Parent wrappers do not add another scroll area. Explicit `scrollMode="viewport"` remains available for existing bounded Card layouts.
- Form/detail content scrolls within the Shell content area. Small embedded tables use `scrollMode="inline"`; place Dialog/Sheet components outside the list layout, or explicitly select inline mode for a table inside an overlay.
- Native containers carry `scroll-region` so Inertia manages navigation scroll positions. Listen to the actual scroll owner instead of `window.scrollY` for header state. Do not duplicate/synchronize scrollbars with JavaScript or require Shift+wheel to reach columns.

## Checks

For failed saves or processing actions, a 5xx must produce a visible message that remains until corrected
or dismissed, using the action's everyday wording. A brief toast or a successful Sentry capture alone
does not satisfy user feedback. Preserve unsaved inputs and keep technical details in server reports.
Use the existing shared API error handler; see `docs/dev/28-pelaporan-kesalahan.md`, "Kegagalan yang terlihat oleh pengguna".

Run package build, type-check, export smoke, consumer builds, and local Docker health checks. Verify light/dark appearance and keyboard/focus behavior in the running Shell. For every changed dialog, open it in the running app: its title and required decision text must be visible in the modal itself, not hidden behind a hover/click hint.
